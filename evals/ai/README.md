# Автономная диагностика AI feedback2req

**Только синтетические данные. Разметка PRELIMINARY, версия 0.2.0; набор 1.1.0.**
Инструмент не вызывает модели, не выбирает провайдера, не зависит от backend,
frontend, worker или PostgreSQL. Это инструмент разработки, не прикладной приём AI.
Объём реализации разрешён пользователем 2026-10-23; содержательная разметка
оставлена для отдельного подтверждения. См. [план](PLAN.md).

Начать содержательное рассмотрение: [разметка S01–S14](REVIEW.md).
Там разделены ожидаемые смыслы, альтернативы, недопустимые выводы и вопросы.
Уточнения пользователя для S01, S02, S03, S06, S09, S12, S13 внесены в редакцию
0.2.0. S08 сохранён без содержательных изменений. Таблица совместимости и
изменений приведена в листе разметки для окончательного согласования.

## Состав

- [Манифест](datasets/synthetic-ru-v1/manifest.json) и 14 сценариев содержат
  46 независимых примеров четырёх операций, включая синтетические транскрипты.
- [Контрольный replay](datasets/synthetic-ru-v1/replays/controls.json) содержит
  сохранённые инженерные ответы. Это не ответы реальной модели и не
  единственно правильные эталоны. Три примера намеренно содержат **смысловые**
  ошибки, которые должны остаться для эксперта: S09/missed-unsupported,
  S09/false-positive, S11/irrelevant-evidence. Структура и связи этих ответов валидны.
  Они явно помечены `fixture_role=intentional_semantic_error`; `semantic_gold=false`
  запрещает интерпретировать весь набор как положительные эталоны качества.
- [Replay ошибок](datasets/synthetic-ru-v1/replays/faults.json) содержит 24
  намеренно ошибочные записи, включая 4 технических сбоя и 3 повреждённых JSON.
  [Ожидаемые коды](datasets/synthetic-ru-v1/replays/fault-expectations.json)
  проверяют сам инструмент, а не качество модели.
- [Проверки](checks.py), [runner](runner.py), [CLI](cli.py) и
  [тесты](tests/test_evaluation.py) не импортируют код приложения.
- [Генератор](build_dataset.py) воспроизводит JSON и лист разметки; без
  `--write` он только сравнивает артефакты с сохранённой версией.

В каждом примере канонические `request` и `fixture_response` отделены от
`trusted`, разметки и экспериментальных метаданных. Эти дополнительные поля
не передаются модели и не добавляются в утверждённые AI-контракты.
Каждый пример — изолированный снимок с отдельными идентичностями/состояниями.
Группировка, генерация и проверка получают фиксированные подготовленные входы;
это не запуск продуктового workflow и не тестирование его оркестратора.
S06 содержит только конфликтующие позиции и не покрывает продолжение независимой
доработки при содержательном конфликте. Проверка S10 относится к техническому сбою.
Для S03 представлены предпочтительное разделение и допустимое объединение;
программного правила «одно требование на одну доработку» не введено.

## Запуск с Python

Подходит Python 3.12. Установку выполнять в отдельное локальное окружение;
глобальные настройки и существующее окружение приложения менять не нужно.
Следующие команды предполагают доступный рабочий `python`:

```text
python -m venv evals/ai/.venv
evals/ai/.venv/Scripts/python.exe -m pip install -r evals/ai/requirements.txt
evals/ai/.venv/Scripts/python.exe -B evals/ai/cli.py validate-dataset
evals/ai/.venv/Scripts/python.exe -B -W error -m unittest discover -s evals/ai/tests -v
evals/ai/.venv/Scripts/python.exe -B evals/ai/build_dataset.py
```

На Linux путь к интерпретатору окружения — `evals/ai/.venv/bin/python`.
Зависимости проверки зафиксированы в [requirements.txt](requirements.txt).
Проблема Python в текущей Windows-среде обойдена настоящим запуском в
одноразовом контейнере; системный Python не ремонтировался и не заменялся.

## Запуск в уже доступном тестовом контейнере

Образ не является зависимостью контура. Здесь использован уже существующий
локальный `feedback2req-checks:latest`, без сборки/изменения Dockerfile или Compose.
Зафиксируйте локальный image ID перед серией проверок, чтобы перестройка тега
параллельным агентом не сменила окружение. Команды PowerShell из корня репозитория:

```powershell
$evalRoot = (Get-Location).Path
$evalImage = docker image inspect feedback2req-checks:latest --format '{{.Id}}'
docker run --rm --network none --mount "type=bind,source=$evalRoot,target=/workspace,readonly" --entrypoint python $evalImage -B -W error -m unittest discover -s /workspace/evals/ai/tests -v
docker run --rm --network none --mount "type=bind,source=$evalRoot,target=/workspace,readonly" --entrypoint python $evalImage -B /workspace/evals/ai/cli.py validate-dataset
docker run --rm --network none --mount "type=bind,source=$evalRoot,target=/workspace,readonly" --entrypoint python $evalImage -B /workspace/scripts/validate_ai_contracts.py
```

Контейнеры имеют отключённую сеть; репозиторий только для чтения, временные
файлы тестов остаются внутри одноразового контейнера. Не требуются БД и сервисы.

## Replay и отчёты

Команды из корня репозитория с рабочим Python:

```text
python -B evals/ai/cli.py replay --input evals/ai/datasets/synthetic-ru-v1/replays/controls.json --output evals/ai/results/controls-001
python -B evals/ai/cli.py replay --input evals/ai/datasets/synthetic-ru-v1/replays/faults.json --output evals/ai/results/faults-001
```

Второй запуск **ожидаемо возвращает 1**, поскольку обнаружены намеренные
нарушения. Успех тестирования инструмента устанавливает unittest, проверяющий
ожидаемые коды каждой такой записи; код 1 не маскируется под успешный replay.

Результат: `report.json`, читаемый `report.md` и `expert-review.json`.
Каталог вывода должен быть новым: существующие результаты не перезаписываются.
Результаты игнорируются Git локальным [.gitignore](.gitignore).

Для контейнерного replay можно оставить вывод в `/tmp/report` для smoke-проверки.
Чтобы сохранить его на хосте, создайте `evals/ai/results`, смонтируйте только
этот каталог вторым bind-mount в `/reports` с правом записи и укажите новый
`--output /reports/controls-001`; весь репозиторий по-прежнему только для чтения.

Коды завершения:

| Код | Значение |
|---|---|
| 0 | В выполненных программных проверках нарушений нет; содержательное качество этим не доказано |
| 1 | Найдены технические, структурные, ссылочные или другие реализованные нарушения |
| 2 | Вход, версия, привязка, конфигурация или сам инструмент не позволили выполнить проверку |

Пример диагностического отчёта не содержит единого балла, проходного порога,
рейтинга или автоматического экспертного вердикта. Категории могут пересекаться:
их числители нельзя складывать как число разных плохих ответов.
Состав назначенных примеров, пропуски, технические исходы и заявленный coverage
учитываются отдельно. Количество находок не используется как мера полноты чтения.

## Формат сохранённых экспериментов

Используйте структуру контрольного replay, сохраняя:

- `format_version`, версии набора/разметки и `dataset_sha256`;
- `mode`: `synthetic_fixture_replay` с `model.name=none` для инженерных фикстур
  либо `saved_model_responses` для отдельно полученных ответов;
- модель и её доступную ревизию; неизвестную ревизию обозначать явно;
- версии шаблона/адаптера, параметры генерации и seed либо `null`;
- `case_id`, `example_id`, номер `attempt`, `request_sha256` каждой записи;
- `outcome=returned` и ровно одно из `response`/`response_file`; либо
  `outcome=failed`, технический `error_code` и отсутствие содержательного ответа;
- `duration_ms`, если известна фактическая длительность исходного вызова.

`created_at` отчёта — время оценки, не выдуманное время исходного AI-вызова.
Пропущенные длительности не подменяются измерением скорости replay.
Повторяющиеся case/example допустимы с разными номерами попыток. Номера replay
не являются ProcessingRun/StageAttempt и не создают новых прикладных запросов.

Путь `response_file` отсчитывается от каталога replay и не может выйти за него,
в том числе через символическую ссылку. Для точного сохранения повреждённого
ответа используйте этот вариант. Дубликаты JSON-полей, NaN/Infinity и обрывы
отклоняются; исходный ответ не нормализуется и не исправляется.

Набор связан хэшем с содержимым всех сценариев и разметки. Запрос каждой записи
проверяется по отдельному хэшу. Отчёт дополнительно фиксирует хэши схем,
проверочного кода и точные версии Python/jsonschema/referencing.
Изменение состава/смысла сценариев требует новой версии набора; изменение
разметки — новой версии разметки. Для регенерации изменить источник в
[генераторе](build_dataset.py) и явно запустить `--write`.
Сохранённые эксперименты со старой привязкой не принимаются молча.

## Экспертная оценка и сопоставление

В `expert-review.json` есть разметка каждого случая и независимые критерии:
поддержка, полнота смысла, отсутствие ложных срабатываний, direct/inferred,
неопределённость/конфликты, серьёзность/блокировка и устойчивость.
Для S03 и S12 дополнительно есть `claim_reviews`: отдельные содержательные
вердикты по каждому указанному существенному утверждению. В S12 доступная цитата
о фильтрах не доказывает синхронизацию; при полной утрате доступных свидетельств
нет для обеих частей. Список утверждений — предварительная экспертная разметка,
не автоматически установленная истинность или новый формат AI-контракта.
В `claim_reviews` используются те же verdict/rationale, что и в общих критериях.
Пропущенный/pending вердикт сохраняет статус экспертной записи pending.

Эксперт смотрит **реальный сохранённый ответ и исходный контекст**, а не только
инженерный контрольный ответ. Заполняет `reviewer` и для каждого критерия:

- `met` — критерий выполнен;
- `not_met` — критерий нарушен;
- `uncertain` — информации/согласования недостаточно;
- `not_applicable` — критерий неприменим;
- `pending` — оценка ещё не выполнена.

Любой вердикт, кроме `pending`, требует объяснения в `rationale`. При техническом сбое
содержательные критерии неприменимы. Устойчивость оценивается по паре, указанной
в `relationship`, с сопоставлением смыслов и источников, не буквального текста.
Серьёзность и блокирующее действие не связаны автоматическим соответствием.
`medium` в инженерной фикстуре S09 не является фиксированным эталоном severity
для всех `unsupported_claim`; обоснование значения и scope оценивает эксперт.

```text
python -B evals/ai/cli.py replay --input PATH_TO_REPLAY.json --expert PATH_TO_EXPERT_REVIEW.json --output evals/ai/results/reviewed-001
python -B evals/ai/cli.py compare --left PATH_TO_LEFT_REPORT.json --right PATH_TO_RIGHT_REPORT.json --output evals/ai/results/comparison-001
```

Экспертный лист привязан к набору, версии разметки и конкретному replay,
включая байты внешних файлов ответов. Чужой или устаревший лист отклоняется.
Вердикты остаются **предварительными**, даже если все поля заполнены.
`reference_fixture_role` описывает сохранённую инженерную фикстуру, а не
содержательное качество импортированного ответа модели. Намеренные смысловые
ошибки не становятся положительными эталонами при успешной проверке схемы.
`uncertain` не превращается в `met`; инструмент не утверждает разметку.
Численные precision/recall не вычисляются из совпадения строк или числа объектов:
нужны согласованные смысловые единицы и экспертное сопоставление.

`compare` сопоставляет только одинаковые входы/попытки с одинаковыми версиями
набора, разметки, схем и инструмента. Иначе возвращает 2. Показывает отдельные
категории по сценариям без выбора победителя. Разные конфигурации отмечаются:
такую разницу нельзя приписывать только модели. Экспертные содержательные
вердикты остаются в исходных отчётах и не смешиваются с автоматическими ошибками.

## Реализованные проверки и границы

| Область | Программно | Что остаётся экспертным или интеграционным |
|---|---|---|
| Структура | Восемь входных/выходных схем, закрытость объектов, обязательные поля | Семантика текста |
| AP-01–AP-04 | Проект/состояния по trusted-фикстуре, уникальные ключи, точные цитаты, все вхождения, Unicode code points, координаты и сопоставление времени | Реальные права, состояния БД и точность ASR |
| AP-05–AP-06 | Наследуемая надёжность фрагмента, типы связей и принадлежность выбранных оснований | Поддержка всего утверждения, надёжность интерпретации |
| AP-07–AP-08 | coverage по основным ключам, причины пустого результата, состав групп, позиции внутри группы | Полнота фактического чтения, смысловая близость и действительный конфликт |
| AP-09 | Снимок сравнений, роли/состав, собственная редакция, неполный поиск дублей | Смысловой дубль, отсутствие глобальных утверждений в свободном тексте |
| AP-10 | Типы ключей, область вопросов, связи questions/issues, согласованность категорий и checks | Существенность, серьёзность и обоснованность блокировки |
| AP-11–AP-14 | Неизменённость переданного исторического контекста, минимальная форма deleted_source, отсутствие архивного текста удалённого источника в trusted, число прежних открытых блокеров | Гонки публикации, настоящее удаление/очистка, жизненный цикл и решения человека |

Сегментный временной интервал наследуется из синтетического сопоставления;
пословная точность не изобретается. В этом наборе trusted хранит полный
текст соответствующего состояния и одно сегментное сопоставление. Более точное
выравнивание не моделируется. Математически целые JSON-числа (`0.0`) принимаются,
если их принимает утверждённая JSON Schema; сохранённый документ не переписывается.

Для `extract_feedback` частичность запрещена схемой. Для проверки дублей
пропуски определяются по предусмотренному набору и `considered_keys`.
Частичность других операций без определимого внешнего плана подединиц отмечается
как `PARTIAL-UNITS-UNRESOLVED`; готового продукта для принятия такого плана здесь нет.

## Данные и конфиденциальность

Контур предназначен **только для синтетического набора**. `trusted` — фиктивные
факты теста, не источник полномочий и не архив реального проекта.
Отчёты не копируют запросы/ответы, цитаты, тексты замечаний или свободные
экспертные пояснения. Диагностика содержит коды и безопасные JSON-пути; ошибки
валидатора с исходными значениями и traceback не печатаются.

В экспертном листе есть только предварительная синтетическая разметка; внесённые
человеком пояснения остаются в этом листе. Не помещать секреты в модельные имена,
версии, параметры или пояснения. Имена полей настроек ограничены; credentials не
предусмотрены. Сырые ответы сохраняет явно подготовленный вход replay, сам
инструмент не создаёт долговечный журнал сырых данных.

Удаление проекта/источника не может обходиться экспериментальными архивами.
Историческая связь deleted_source содержит только ID и факт удаления; полный
текст, позиции, время и хэш удалённого фрагмента в неё не добавляются.
Использование реальных данных и их очистка требуют отдельного согласования;
отсутствие обязательного обезличивания в MVP не разрешает их перенос сюда.

## Следующие шаги

1. Согласовать [предварительную разметку](REVIEW.md), включая спорные случаи.
2. При необходимости уточнить смысловые единицы и метод подсчёта precision/recall.
3. Реальные модельные эксперименты, доступ, бюджет и адаптеры согласовать отдельно.
4. ASR, записи, прикладной приём, конкурентность и удаление проверять в их
   собственных разрешённых этапах. Успешные офлайн-тесты их не заменяют.

Результаты фактической проверки и ограничения: [VALIDATION.md](VALIDATION.md).
