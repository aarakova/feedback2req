# generate_requirements 1.0

Автономная Requirements Generation Agent: проверенный канонический вход →
сменный провайдер → строгий JSON → схема 1.0 → проверка связей → кандидат.
Модуль не сохраняет требования и не вызывает другие продуктовые роли.

Основания: [AI_CONTRACTS §7.3](../../docs/AI_CONTRACTS.md), FR-014–020,
BR-007–013 и [инварианты AI](../../docs/AI_VALIDATION.md).
Потребность, интерпретация и реализация различаются в [prompt](prompt.py),
`text` и `rationale`; новые поля и критерии приёмки не добавлены.

## Запуск

Из корня собственного worktree, Python 3.12 и зависимости [ai](../requirements.txt):

```text
python -m pip install -r ai/requirements.txt
python -B -W error -m unittest discover -s ai/tests -v
python -B -m ai.generate_requirements --request evals/ai/generation/bounded.request.json --synthetic-response evals/ai/generation/bounded.response.json --output generated-requirements.json
python -B evals/ai/generation/replay.py --output evals/ai/results/generation-run
```

CLI работает только в явно обозначенном `synthetic_fixture_replay`, выводит
`model=none; semantic_quality=not_evaluated`. Он проверяет заранее заданный
ответ и не генерирует смысл. Новый файл результата содержит ровно канонический
ответ; существующие файлы и каталоги отчётов не перезаписываются.
Примеры [входа](../../evals/ai/generation/bounded.request.json) и
[выхода](../../evals/ai/generation/bounded.response.json) описывают выгрузку
**при наличии отмеченных записей**, не определяя формат или поведение без отметок.

Набор: [15 контролей и 2 смысловых контрпримера](../../evals/ai/generation/cases.json).
Воспроизведение: `python -B -m evals.ai.generation.build_cases`.
[Результаты и точные команды](../../evals/ai/generation/VALIDATION.md).
Для тестов использован имеющийся Docker image `0c154beef3fd` с `--network none`,
read-only исходниками и отдельным write-mount для локальных отчётов.

## Интерфейс

```python
from ai.generate_requirements import GenerationError, generate_requirements
from ai.generate_requirements.provider import Ollama, OllamaConfig


def form_candidates(canonical_request, verify_against_application_state, config):
    return generate_requirements(
        canonical_request,
        Ollama(config),
        verify_context=verify_against_application_state,
    )


# Подготовка конфигурации; эта конфигурация запрещает вызов сервера.
config = OllamaConfig(
    endpoint="http://127.0.0.1:11434/api/chat",
    model="MODEL_NOT_SELECTED",
    transfer_enabled=False,
    timeout_seconds=60,
    temperature=0,
    think=False,
)
```

Модель не выбрана; её эксперимент ведётся отдельным направлением. Реальные
вызовы требуют согласования модели, провайдера и передачи данных. Нет загрузки
весов, облачного fallback или неявной передачи. Флаг передачи сам по себе не
является согласием. Поддержку схемы/режима think выбранным сервером нужно
испытать отдельно; loopback URL не доказывает локальность весов.

`GenerationProvider.generate(request) -> str | bytes` возвращает канонический
JSON. Адаптер Ollama переиспользует транспорт группировки: gate, bounded read,
timeout, отключение ambient proxy, запрет redirect, `format` и system/user.
В транспорт добавлены только точки выбора prompt и схемы; прежняя группировка
продолжает использовать собственные значения. Строгий парсер, снимки и общие
проверки входа также переиспользованы. Зависимость от evaluator отсутствует.
При упаковке нужно сохранить пакет `ai` и утверждённые схемы
`docs/contracts/ai/v1/` относительно его корня, как для группировки.

## Прикладной приём

`generate_requirements` возвращает изолированный `dict` после проверки всего
кандидата. `validate_request`/`validate_response` — локальные проверки структуры
и связности; они не устанавливают права или смысловую истинность.

Проверяются:

- Версия и операция, закрытые объекты, обязательные и необязательные поля.
- Уникальность всех `key` запроса и всех `local_id` ответа, включая аннотации.
- Замыкание evidence находок, групп/конфликтов и прежних редакций.
- Длины Unicode-фрагментов/выдержек, согласованность source/text refs и интервалов.
- Ровно одна coverage-запись на находку; пропущенное не используется как
  рассмотренное. Находка `completed`, не выбранная в evidence ни одного
  кандидата, требует причины, даже если другие кандидаты присутствуют.
- `considered_keys` содержит только рассмотренные находки; выбранные
  EvidenceSelection относятся к ним и ссылаются только на переданные
  доступные фрагменты этой находки. Группа, документ или прежняя редакция
  не подменяют evidence. `context_keys` — только группы и документы.
- Существование related-ссылок и область вопросов: входные находки, группы,
  прежние редакции либо выходные кандидаты. Фрагмент и документ сами по себе
  не задают область блокировки.

Поддерживаются один/несколько кандидатов, несколько оснований, один-ко-многим
в обе стороны, успешное отсутствие кандидатов, прежние кандидаты и повторное
формирование. Все findings/fragments/groups/documents передаются без скрытого
урезания. `previous_candidates` — контекст, не команда перезаписи.

Неполный набор явно представлен смесью `completed`, `insufficient_information`
и `not_processed`. Пригодные независимые кандидаты сохраняются. Частичность
внутри одной находки (`partially_processed`) отклоняется как
`invalid_response:partial_scope_unverifiable`: нет доверенного плана подединиц,
требуемого §6 контракта. Автоматического разбиения/агрегации нет.
Декларация completed не доказывает фактического прочтения всей находки моделью.

Историческая `deleted_source` сохраняет происхождение, но не становится
доступным evidence. Входная схема требует минимум одну находку и один доступный
фрагмент. При полной утрате всех фрагментов приложение не должно фабриковать
запрос; нужно показать недостаток доступных оснований вне AI-вызова.

Нужен вопрос вместо уверенного кандидата при неопределённом ожидаемом изменении,
значимой неизвестности внутри ситуации, существенном конфликте, зависимости
смысла от ненадёжной речи или неразрешённом расхождении с документацией.
Неизвестное вне описанных условий допускает ограниченный кандидат и при
необходимости информационный вопрос. Это содержательные правила prompt и
экспертной оценки; наличие поля JSON само по себе их не доказывает.

`GenerationError.code`: `invalid_request`, `invalid_response`, `timeout`,
`provider_error`; `rule` — безопасный код причины. Технический сбой не получает
вымышленного coverage. Ответ не ремонтируется, его невалидные части не
отбрасываются молча. Нет автоматического retry или постоянных сырых логов.
Вход/ответ/транспортная оболочка ограничены 1 MiB каждый без усечения.

## Граница будущего backend после F2

Обязательный `verify_context(request) -> None` вызывается **до** провайдера,
получает копию и должен выбросить исключение при любой непрошедшей проверке.
Возврат False не является отказом: результат callback не используется.
No-op verifier допустим только в явно синтетическом replay.

Приложение обязано проверить по доверенному состоянию:

1. Право запуска, членство и единую проектную область каждого объекта,
   актуальность точных refs и связь `request_id` с конкретной попыткой/снимком.
2. Доступность и принадлежность выбранных фрагментов находкам, точную цитату
   и координаты по исходному состоянию, source/text mapping и надёжность речи,
   авторство, документы, группы и неизменённые прежние редакции. Одна лишь
   совпавшая длина цитаты или существование ключа этого не подтверждает.
3. После AI-вызова повторно проверить разрешения, активность попытки, выбранные
   состояния и доступность. Принять и сохранить результат атомарно; не удерживать
   блокировки во время inference. Устаревший ответ не становится текущим.
4. Связать local_id с постоянными ID/редакциями средствами будущего backend;
   сохранить EvidenceSelection, considered/context, полный coverage, вопросы,
   uncertainty и происхождение (provider/model, synthetic/ai_performed,
   версии prompt/адаптера). Не переносить решения человека или закрытие блокеров.
5. Управлять lease/deadline, отменой, идемпотентностью, публикацией и ручным
   повтором. Ошибки неизвестного исхода COMMIT требуют чтения сохранённого
   состояния, а не повторной генерации с новым ID по умолчанию.

Это Python-интерфейс автономной операции, не HTTP/DB-контракт. У F1 изучены
подготовка атомарного входа, приём, heartbeat и повторная проверка перед
публикацией. Опубликованный F2 проверен только чтением на
`20656819aad3a857875ec0d91a263d903c85638b`:
[контракт F2 в его ветке](https://github.com/aarakova/feedback2req/blob/20656819aad3a857875ec0d91a263d903c85638b/docs/FINDING_GROUPS_API.md).
Он хранит группы и exact finding/source/document states, но не является
хранилищем требований. Его prepare/accept нельзя вызывать для генерации
требований. Подключение генератора к worker и хранению требует отдельного этапа.
В этой ветке F2 не объединён и не изменён; backend/frontend не изменяются.

Смысловую поддержку, достаточность каждой части, отсутствие потерянных условий,
вымышленных решений и корректность блокировки проверяют AI и человек.
[Научные расширения и следующий этап verify](../../docs/research/generation-contract-evolution.md).
