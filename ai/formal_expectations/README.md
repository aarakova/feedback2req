# Формальная классификация пар ожиданий, версия 1

Автономный детерминированный компонент, без LLM, backend, БД, worker и сети.
Он классифицирует **подготовленные структурированные атомарные ожидания** в
явно заданной модели. Он не является четвёртой продуктовой AI-ролью и не
утверждает требования за человека.

Научный источник, названный в поручении: «Правило классификации пар
пользовательских ожиданий при неполных сведениях». Текст статьи/вложение при
реализации **недоступен**. Здесь реализованы правила из задания пользователя,
а не проверенное полное воспроизведение опубликованного метода. Сверка с
оригиналом остаётся следующим исследовательским этапом.

## Установка и запуск

Python 3.12+, единственная runtime-зависимость: `z3-solver==4.15.4.0`.
Инструмент разработки: `ruff==0.11.13`; тесты используют стандартный `unittest`.
Зависимости приложения и общие AI-зависимости не меняются.
Из корня **собственного worktree**:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r ai/formal_expectations/requirements-dev.txt
.venv/Scripts/python.exe -B -m ai.formal_expectations ai/formal_expectations/examples/K.json
.venv/Scripts/python.exe -B -W error -m unittest discover -s ai/formal_expectations/tests -v
.venv/Scripts/python.exe -m ruff check ai/formal_expectations
.venv/Scripts/python.exe -m ruff format --check ai/formal_expectations
```

Linux/macOS: заменить `.venv/Scripts/python.exe` на `.venv/bin/python`.
Можно передать JSON через stdin вместо пути: `python -m ai.formal_expectations -`.
CLI возвращает один JSON: код выхода 0 для D/K/S/U, 2 для любого отказа
(ошибки аргументов argparse выводятся в stderr). CLI ничего не записывает.

На машине разработки Windows Python launcher недоступен. Для фактической
проверки использован уже доступный образ `feedback2req-checks` с неизменяемым ID
`sha256:0c154beef3fd…`, Python 3.12.15, и **отдельный** Linux venv
`.local/formal-venv`, смонтированный в `/env`. Новые зависимости установлены
только туда. Полный ID и результаты фиксируются в [VALIDATION.md](VALIDATION.md).
Пример повторного запуска после создания этого окружения:

```powershell
$formalRoot = (Get-Location).Path
$formalEnv = Join-Path $formalRoot '.local/formal-venv'
docker run --rm --network none --mount "type=bind,source=$formalRoot,target=/workspace,readonly" --mount "type=bind,source=$formalEnv,target=/env,readonly" --workdir /workspace --entrypoint /env/bin/python 0c154beef3fd -B -W error -m unittest discover -s ai/formal_expectations/tests -v
```

## Формальная область

`e = (o, p, C, A, s)`:

- `object_id`, `parameter_id` — точные идентификаторы **уже сопоставленных**
  объекта и одного параметра. Оба ожидания должны совпасть с `model`.
  Синонимы, связи объектов и достоверность сопоставления не устанавливаются Z3.
- `C` — непустое подмножество конечного явно перечисленного `model.situations`.
  Ситуация — атомарная, взаимоисключающая с другими метка состояния мира.
  `online`/`offline` в примерах именно такие состояния, а не произвольные теги.
  Для пересекающихся предикатов поставщик обязан заранее построить атомарное
  разбиение. Числовые/булевы условия можно заранее перечислить такими случаями;
  произвольный язык предикатов условий не поддержан.
- `A` — непустое множество значений одного параметра: булево, перечислимое
  или замкнутый числовой интервал с рациональными границами внутри заданного домена.
- `s` (`basis`) — обязательная непустая непрозрачная ссылка на основание.
  Модуль сохраняет её во входе, но не проверяет наличие/истинность свидетельства.
  Основание не участвует в логическом пересечении.

Пустые собственные C/A, перевёрнутые интервалы, выход за домен — ошибки
формализации, не D или K. Множество значений каждого ожидания независимо от C:
условно-зависимые ограничения требуют внешнего разбиения на атомарные пары.
Поле вроде `depends_on`/`formula` отвергается; незаявленную семантическую зависимость
по одним числам модуль обнаружить не способен.

Для каждой полной допустимой пары строятся **два отдельных** запроса Z3:

1. `Domain_C(c) ∧ C_left(c) ∧ C_right(c)`;
2. `Domain_A(a) ∧ A_left(a) ∧ A_right(a)`.

Оба запроса выполняются даже для D. Символы условий — ограниченные целые индексы,
enum — ограниченные индексы, bool — Z3 Bool, интервалы — Z3 Real с точными
рациональными границами. Между запросами переменные не связаны. Ввод не
передаётся интерпретатору Python, SMT-LIB или парсеру произвольных выражений.

| Условия | Значения | Класс |
|---|---|---|
| unsat | sat или unsat | D |
| sat | unsat | K |
| sat | sat | S |

`S` означает существование общего значения в общей ситуации. Оно не доказывает
эквивалентность, включение ожиданий или пригодность продуктового решения.
Проверяется пара; глобальная совместимость совокупности не следует из всех S:
`{a,b}`, `{b,c}`, `{a,c}` совместимы попарно, но не имеют общего значения втроём.
Случай 19 и тест показывают это без реализации глобального классификатора.

## Контролируемый JSON-интерфейс

Это **локальный формат компонента** `format_version: "1"`, не расширение
утверждённых AI-контрактов 1.0. Все объекты закрыты, все показанные поля обязательны;
только верхнее поле `omega` необязательно. Полный вход:

```json
{
  "format_version": "1",
  "model": {
    "object_id": "product:export",
    "parameter_id": "latency",
    "situations": ["online", "offline"],
    "domain": {
      "kind": "interval", "lower": "0", "upper": "100",
      "unit": "s", "dimension": "time"
    }
  },
  "left": {
    "object_id": "product:export", "parameter_id": "latency",
    "conditions": ["online"],
    "values": {"kind": "interval", "lower": "1", "upper": "3", "unit": "s"},
    "basis": "synthetic:finding-left"
  },
  "right": {
    "object_id": "product:export", "parameter_id": "latency",
    "conditions": ["online"],
    "values": {"kind": "interval", "lower": "5", "upper": "10", "unit": "s"},
    "basis": "synthetic:finding-right"
  }
}
```

Варианты domain/values:

```json
{"kind": "boolean", "allowed": [false, true]}
```

```json
{"kind": "enum", "allowed": ["manual", "automatic"]}
```

Для bool domain содержит оба значения; `values.allowed` — непустое подмножество.
Для enum domain перечисляет всю конечную область; values — её подмножество.
Повторяющиеся элементы запрещены, порядок множеств не влияет на результат.

Числа: целые JSON или десятичные строки, не более 64 символов, без экспонент,
NaN/Infinity/float. Замкнутые интервалы могут иметь одинаковые границы.
Единицы нормализуются точной рациональной арифметикой:

| Размерность | Поддержанные единицы | Каноническая |
|---|---|---|
| dimensionless | 1 | 1 |
| time | s, ms, min | s |
| length | m, cm, mm | m |
| mass | kg, g | kg |

Совместимые единицы конвертируются, например 300 ms = 0.3 s. Разные размерности
отвергаются; неизвестные единицы не угадываются. Аффинные шкалы, составные единицы,
погрешности измерений и целочисленные числовые домены не реализованы.

## Неполные сведения и Ω

Неизвестное **целое поле C или A** обозначается JSON `null`, а не отсутствием
поля/пустым множеством/универсумом. Частичные верхние/нижние оценки множеств
в этой версии не кодируются. `object_id`, `parameter_id`, `basis` и model
должны быть известны до вызова. Нет автоматического восстановления данных.

При неизвестном поле обязателен `omega`:

```json
{
  "complete": true,
  "variants": [
    {
      "left": {"conditions": ["online"], "values": {"kind": "interval", "lower": "1", "upper": "3", "unit": "s"}},
      "right": {"conditions": ["online"], "values": {"kind": "interval", "lower": "5", "upper": "10", "unit": "s"}}
    },
    {
      "left": {"conditions": ["offline"], "values": {"kind": "interval", "lower": "1", "upper": "3", "unit": "s"}},
      "right": {"conditions": ["online"], "values": {"kind": "interval", "lower": "5", "upper": "10", "unit": "s"}}
    }
  ]
}
```

Полный запрос — [пример U](examples/U.json): его `left.conditions = null`.
У каждого варианта C/A заданы полностью, входят в домены, и **все ранее известные
поля совпадают** с исходными (с точностью до порядка множеств и единиц).
Фиксированные объект/параметр/основание не могут переопределяться вариантом.
Произвольные зависимости между возможными заполнениями задаются самим списком
полных пар; декартово произведение независимо выбранных догадок не создаётся.
Любой некорректный вариант отвергает весь запрос до вычисления; он не удаляется
молча из Ω. Для полной пары без `omega` используется единственный исходный вариант.

`complete: true` — **обязательство поставщика модели**, что список задаёт всё
допустимое Ω в выбранной предметной модели. Это не обнаруженная Z3 полнота
относительно реальности. Локальная предметная модель ограничивается доменами
и явно перечисленными допустимыми парами. Дополнительные предметные правила
поставщик обязан проверить до подачи и отразить в выборе Ω. Неограниченное или
символическое Ω не поддержано. Неполный список с `complete: false` не даёт класса.

После проверки всех вариантов один наблюдавшийся класс даёт D/K/S; разные
классы дают U. Даже после обнаружения двух классов проверка продолжается:
последующий отказ не выдаётся за завершённый анализ. Пустое Ω — ошибка.
Для непустого Ω' ⊆ Ω при неизменных model/известных данных однозначный класс
сохраняется, поскольку множество классов Ω' — непустое подмножество одноэлементного
множества классов Ω. U при добавлении сведений может стать однозначным.

## Python API, результаты и технические отказы

```python
from ai.formal_expectations import Limits, analyze

result = analyze(request_dict_or_json_bytes, limits=Limits(max_variants=128))
if result.status == "classified":
    print(result.classification, result.observed_classes)
else:
    print(result.diagnostic.code, result.diagnostic.rule)
json_result = result.to_dict()
```

`Analysis` — неизменяемая структура. Успех: `status=classified`,
`classification=D|K|S|U`, `complete=true`, `diagnostic=null`.
`variants_checked/total`, `observed_classes` и `checks` фиксируют объём.
У `checks` есть индекс варианта (с нуля), вид пересечения и исход sat/unsat.
Объяснение отражает формальную операцию, не истинность исходного отзыва.

При отказе всегда `status=failed`, `classification=null`, `complete=false`.
Наблюдённые классы/проверки сохраняются как частичные диагностические сведения
и **не являются доказанным итоговым классом**. До завершения валидации total
может быть null. Публичные ошибки не содержат текст ввода/native exception.

| diagnostic.code | Значение |
|---|---|
| invalid_input | Повреждённый JSON, дубликаты ключей, неверный тип/обязательное поле |
| invalid_formalization | Пустое Ω/C/A, неверный интервал/домен/единицы, противоречивое уточнение |
| not_comparable | Разные объекты или параметры |
| unsupported_input | Версия/единицы/конструкции вне контролируемой грамматики |
| incomplete_omega | Неизвестное без Ω либо список не объявлен полным |
| resource_limit | Варианты, вызовы, сложность/размер JSON, Z3 rlimit/memory |
| solver_unknown | Z3 unknown без установленного timeout/resource; canceled тоже не угадывается |
| timeout | Общий deadline, Z3 reason=timeout или TimeoutError |
| solver_failure | Исключение native Z3 |
| internal_failure | Непредвиденная внутренняя ошибка |

`unknown`/timeout/отказ никогда не преобразуются в U.

По умолчанию: 256 вариантов, 512 вызовов решателя, общий deadline 5000 ms,
timeout одного решателя 1000 ms, rlimit 100000 на запрос, Z3 max_memory 128 MiB,
вход ≤1 MiB; глубина JSON ≤24, ≤50000 узлов, коллекция ≤4096 элементов,
строковые идентификаторы/основания ≤256 символов. Все `Limits` — положительные
32-bit int; CLI предоставляет одноимённые параметры с дефисами, например
`--max-variants 64 --solver-rlimit 10000 --total-timeout-ms 2000`.

Deadline проверяется до/после native-вызова и при обходе входа. Это кооперативный
предел, а не обещание жёстко прервать произвольный зависший native-код. Z3 memory
limit — средство самого решателя, не изоляция памяти процесса/всех параллельных
вызовов. Для недоверенного сервиса нужны отдельный процесс и внешние OS/container
лимиты; сервис в этой задаче не реализован. У каждого анализа свой Z3 Context,
глобальные параметры не меняются; библиотеки/окружение остаются частью доверенной базы.

## Будущая интеграция: только предложение

Qwen может сформировать **кандидат** этого JSON, но не подтверждает сопоставимость,
полноту Ω, достоверность основания или предметную модель. Будущий прикладной
адаптер должен проверить разрешённые снимки находок/свидетельств, сохранить
неизвестные и пройти валидацию. Отсутствующие значения/варианты нельзя
достраивать автоматически; невалидный/неполный кандидат остаётся диагностикой.
Незавершённый Qwen-код не импортируется и не подключается.

В существующей архитектуре разумная точка вызова — прикладной анализ пар
потенциальных конфликтующих позиций после получения валидированного кандидата
`group_findings` и явной формализации человеком/доверенным адаптером, **до
представления вывода человеку**. Это вспомогательная проверка одной операции
Feedback Analysis Agent, без прямых вызовов продуктовых агентов друг другом.
D/S не удаляют смысловой конфликт автоматически, K не создаёт HumanDecision,
U не равнозначно `insufficient_information` всей находки. Не меняются coverage,
принятие/публикация, блокеры, provenance или полномочия worker/F2.

Текущие закрытые [AI-контракты 1.0](../../docs/AI_CONTRACTS.md) имеют
`ConflictCandidate(local_id, description, positions)` и uncertainties/questions, но не
типизированные model/Ω/Z3 checks/diagnostic. Нельзя добавлять технический объект
в эти ответы или выдавать его текстовую упаковку за согласованное хранение.
**Предложение отдельного решения:** версионированный результат формальной
проверки в прикладном слое, связанный с точными состояниями двух находок,
версиями формализации/модели и полным входом Ω; отдельно класс/полнота/diagnostic,
версии решателя и лимиты. Привязки должны соблюдать действующие права и удаление
источников. Ни DTO, ни схема хранения, ни новый API этим предложением не утверждены.

Следующий этап: получить статью, сверить предпосылки и формализм, затем отдельно
согласовать подготовку/проверку структурированных ожиданий и хранение результата.
Только после этого проектировать интеграцию с Qwen и F2.
