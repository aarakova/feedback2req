# group_findings 1.0

Автономная операция Feedback Analysis Agent: канонический запрос → сменный
провайдер → строгий JSON → локальная JSON Schema → прикладные инварианты → кандидат.
Семантическую группировку выполняет модель по [prompt](prompt.py).
`Replay` возвращает заранее заданный ответ и не выполняет смысловой анализ.

Реализация основана на [утверждённом контракте](../../docs/AI_CONTRACTS.md),
§6, §7.2, AP-02–08/10/13. Схемы 1.0 не изменены. Результат не является
подтверждением качества AI или готовности к production.

## Локальный запуск

Из корня **этого worktree**, с Python 3.12 и зависимостями:

```text
python -m pip install -r ai/requirements.txt
python -B -W error -m unittest discover -s ai/tests -v
python -B -m ai.group_findings --request evals/ai/grouping/compatible.request.json --synthetic-response evals/ai/grouping/compatible.response.json --output grouping-result.json
python -B evals/ai/grouping/replay.py --output evals/ai/results/grouping-run
```

CLI работает только в явно обозначенном `synthetic_fixture_replay`; выводит
`model=none`, `semantic_quality=not_evaluated`. Существующий файл результата и
каталог отчёта не перезаписываются. `grouping-result.json` содержит сам
канонический ответ, без технических полей. Выберите свободное имя при повторе.
Файл результата содержит производный текст: не используйте его как постоянный
журнал пользовательских материалов.

Синтетические примеры: [вход](../../evals/ai/grouping/compatible.request.json),
[ответ](../../evals/ai/grouping/compatible.response.json),
[восемь сценариев](../../evals/ai/grouping/cases.json).
Их можно воспроизвести через `python -B -m evals.ai.grouping.build_cases`.

На текущей машине использован уже имевшийся Docker-образ
`feedback2req-checks:latest`, ID `0c154beef3fd`, без установки зависимостей,
с `--network none`, read-only mount репозитория и отдельным write-mount для
отчётов. Подробности и результаты: [VALIDATION](../../evals/ai/grouping/VALIDATION.md).

## Граница интеграции с F2

```python
from ai.group_findings import group_findings
from ai.group_findings.provider import Ollama, OllamaConfig


def run_grouping(canonical_request, verify_against_application_state, approved_config):
    provider = Ollama(approved_config)
    candidate = group_findings(
        canonical_request,
        provider,
        verify_context=verify_against_application_state,
    )
    return candidate
```

Это интерфейс Python внутри будущего worker, не новый HTTP/API-контракт.
Вход имеет только пять утверждённых полей, `input` передаётся целиком без
нормализации текста, скрытого урезания и самостоятельного получения контекста.
`previous_groups` необязателен. Модуль не зависит от backend/FastAPI/БД или
оценочного контура; при упаковке нужно сохранить рядом утверждённые схемы по
пути `docs/contracts/ai/v1/` относительно корня пакета `ai`.

Обязательный `verify_context(request) -> None` получает изолированную копию.
Он должен **выбросить исключение**, если проверка не пройдена; возвращаемый
результат не используется. Это ответственность прикладного слоя:

1. Проверить право запуска и доступа, принадлежность всех объектов одному
   проекту и связь `request_id` с точным снимком выбранных состояний.
2. Сверить `ref`, `source_ref`, `text_ref`, доступность, авторство, надёжность,
   принадлежность выбранных фрагментов находкам, точные цитаты/Unicode-координаты
   и временное сопоставление с доверенными данными приложения. Модуль проверяет
   замыкание ссылок и длины, но не может проверить истинность входа без хранилища.
3. После AI-вызова повторно проверить актуальность и доступность и атомарно
   опубликовать кандидат только для активной попытки. Не держать блокировки
   во время вызова. Связать локальные ID с постоянными средствами F2.
4. Сохранить весь фактический `coverage`, вопросы и неопределённости; не считать
   наличие групп полным охватом. Не перезаписывать правки человека, прежние
   группы, решения или старые блокеры. Учитывать находку один раз в аналитике,
   даже если она входит в несколько групп.

No-op verifier допускается только для явно синтетических локальных фикстур;
он не проверяет разрешения, проект или актуальность. Тесты проверяют порядок
вызова и отказ verifier, но не доказывают реальную изоляцию backend.
Публикация, сохранение, повтор и отмена принадлежат worker/F2, а не модулю.

## Результаты и ошибки

`group_findings(...)` возвращает новый канонический `dict` только после приёма
всего кандидата. Вход и объект verifier/адаптера изолированы копиями.
Локальная проверка контролирует уникальность всех ключей/ID, coverage,
существование и роли ссылок, `considered_keys`, состав конфликтов, scope
вопросов, замыкание прежних групп и отсутствие потери completed-находок.
Документы допускаются только в `context_keys`, находки — в составе групп.
Многие-ко-многим связи допустимы. Пустые группы с явно негруппированными
находками — успешная классификация, а не технический сбой.

`GroupingError.code` — `invalid_request`, `invalid_response`, `timeout`,
`provider_error` (ошибка настройки также `provider_error`); `rule` — безопасный
код диагностики. Невалидный ответ целиком отклоняется без исправления или
удаления неудобных частей. Технический сбой не превращается в вымышленный
ответ с coverage. Повторов и сохранения сырого текста в логах нет.

Неполный набор обрабатывается явно: принятые `completed`/`insufficient_information`
могут соседствовать с `not_processed`; результаты первых сохраняются, а пробелы
остаются в coverage. Полностью нерассмотренный набор тоже может быть структурно
валиден — вызывающий код не должен сообщать пользователю об успешном анализе.

Внутренняя частичность одной находки (`partially_processed`) отклоняется как
`invalid_response:partial_scope_unverifiable`: этот одиночный вызов не имеет
доверенного плана подединиц, требуемого §6 контракта. Автоматические пакеты и
составление такого плана не реализованы. Схема и разрешённые ею значения при
этом не меняются; это ограничение текущего исполнителя.

Вход, канонический ответ и транспортная оболочка ограничены 1 MiB каждый;
превышение отвергается без урезания. Это локальный технический предел, не
новое ограничение AI-контракта. Лимит токенов и реальный охват чтения модели
не измерены; перед использованием нужно проверить отсутствие усечения на
стороне выбранного сервера и достаточность контекста.

## Реальная модель

[Сравнение моделей и оборудования](MODEL_SELECTION.md) — отдельная
предварительная рекомендация. Реальная модель не запускалась.
Адаптер подготовлен для Ollama `/api/chat`, как в F1: `stream=false`,
самодостаточная `format`-схема, независимые system/user сообщения, ограничение
размера ответа, timeout, запрет redirect и отключение ambient proxy.
Включение `transfer_enabled=True` требует предварительного согласования
модели, сервера и условий передачи данных; флаг сам по себе согласованием
не является. Конфигурация по умолчанию запрещает передачу.

Подготовленный пример **конфигурации, не выполненного запуска**:

```python
config = OllamaConfig(
    endpoint="http://127.0.0.1:11434/api/chat",
    model="qwen3:4b",  # точный digest/квантизацию зафиксировать перед оценкой
    transfer_enabled=False,  # изменить только после согласования
    timeout_seconds=300,
    temperature=0.7,
    think=False,
)
```

Нужно локальное исполнение весов; loopback URL сам по себе не гарантирует,
что модель не облачная. Версию Ollama и поддержку `think`/сложной схемы
нужно подтвердить на выбранном сервере. Неструктурированный/усечённый ответ
отклоняется; удалять Markdown/`<think>` из ответа автоматически нельзя.

Детерминированные проверки не устанавливают смысловую правильность групп,
истинность конфликта, достаточность основания, сохранение всех важных различий
или устойчивость модели к prompt injection. Это отдельная экспертная оценка
на одинаковых входах, с сохраняемой предварительной разметкой.
