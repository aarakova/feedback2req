# Серверное подключение автономных AI-компонентов 1.0

Проверка границы, 2026-11-21. Описаны существующие Python-интерфейсы и
обязанности приложения по [AI_CONTRACTS](../docs/AI_CONTRACTS.md), §§3–10,
AP-01–14. Это не утверждение HTTP API, таблиц требований, очереди или модели.
Продуктовые роли и JSON Schema 1.0 не меняются.

Генератор и проверка готовы к отдельному этапу серверной интеграции как
автономные библиотеки с заменяемым провайдером. Полного серверного сценария
генерация → сохранённая редакция → проверка → решение человека пока нет.
F2/F3 обеспечивают группы/их обработку; их prepare/accept не являются
контрактами генерации или проверки требований.

## Вызовы, входы и выходы

| Операция | Python-интерфейс | Канонический вход | Канонический результат |
|---|---|---|---|
| generate_requirements | [generate_requirements](generate_requirements/service.py) | `findings[1+]`, `fragments[1+]`, `groups[]`, `documents[]`; необязательные `previous_candidates[]`, `change_reason` | `result.requirements[]`: `local_id`, `title`, `text`, `rationale`, `evidence`, `considered_keys`, `context_keys` |
| verify_requirement | [verify_requirement](verify_requirement/service.py) | `target: RevisionView`, `findings[]`, `fragments[]`, `documents[]`, `comparisons[]`, `comparison_scope`, `previous_checks[]`; условно необходимые `prior_decision`, `change_context`, `followup` | `result.checks[4]`, `result.issues[]` |

Оба запроса содержат `contract_version="1.0"`, соответствующую `operation`,
`project_id`, `request_id`, `input`. Оба ответа — только `coverage`,
`uncertainties`, `questions`, `result`; техническая оболочка в них не добавляется.
Полный состав закрытых объектов задают [схемы](../docs/contracts/ai/v1/).

```python
from ai.generate_requirements import generate_requirements
from ai.verify_requirement import verify_requirement

# providers и callback выбирает приложение. Эти вызовы не вызывают друг друга.
generation = generate_requirements(
    generation_request,
    generation_provider,
    verify_context=check_generation_application_state,
)

# verification_request отдельно собран для реально сохранённой точной редакции.
verification = verify_requirement(
    verification_request,
    verification_provider,
    verify_context=check_verification_application_state,
    required_context=required_history_fields,
    review_plan=trusted_execution_plan,
)
```

`GenerationProvider.generate(dict)` и `VerificationProvider.verify(dict)`
возвращают `str | bytes` с каноническим JSON. Сервис возвращает проверенный
`dict`, делает один вызов и принимает ответ целиком. Запрос изолирован копиями
от callback и провайдера. Строгий парсер не исправляет JSON, повторные свойства,
неизвестные поля, NaN/Infinity, превышение размера или неполный ответ.
Лимит запроса, ответа и транспортной оболочки — 1 MiB каждый, без усечения.

Сохранённые примеры и CLI: [генератор](generate_requirements/README.md#запуск),
[проверка](verify_requirement/README.md#запуск). Replay возвращает заранее
подготовленный ответ; ни один такой запуск не выполняет смысловой inference.

## Обязательная доверенная привязка до вызова

`verify_context(request) -> None` — обязательный keyword-only callback.
При отказе он **выбрасывает исключение**. Возврат `False` игнорируется и не
означает отказ; no-op разрешён только в явно синтетических тестах.
Исключение callback преобразуется в безопасный `context_not_verified` до
провайдера. Наличие параметра само по себе не доказывает правильность verifier.

Приложение связывает `request_id` с попыткой и доверенным снимком и проверяет:

1. **AP-01–03.** Полномочия, доступность проекта, принадлежность всех объектов
   одному проекту, точные refs/states, отсутствие подмены актуальной версией.
   Существование UUID или совпадение текста не подтверждают эти факты.
2. **AP-04–06,13.** По сохранённому тексту и разрешённому сопоставлению сверяются
   quote и `[start,end)` в Unicode code points, source/text refs, интервалы речи,
   reliability и авторство. Модуль проверяет длину/структуру и локальные связи,
   но не располагает исходным хранилищем. Это касается также прежнего контекста.
   Доступные evidence действительно принадлежат выбранной находке; группы и
   документы не становятся самостоятельными основаниями. `deleted_source`
   сохраняет только ID/факт удаления, без восстановления цитаты.
3. **AP-07–10.** Предусмотренные единицы и границы контекста собраны полностью.
   Для verification default project_snapshot включает текущие неотклонённые
   редакции, незавершённые предложения и новые принятые кандидаты. Точная цель
   исключена; роли объединены для одной редакции. Selected имеет явную причину.
4. **AP-12,14.** Прежние проверки, открытые issues/вопросы, решения и разрешения
   правдивы и полны. Для генерации previous_candidates замкнуты на выбранные
   findings/fragments и не разрешают замену редакций/перенос решений. Для verify
   нужные `prior_decision`, `change_context`, `followup` определяются по состоянию
   приложения, а не по их отсутствию в запросе. `required_context` — доверенный
   `frozenset` из этих трёх имён; по умолчанию пустой набор не доказывает,
   что истории нет. Неизвестные refs решения/base проверяет приложение.

`evals/ai/checks.py` проверяет только доверенные **синтетические** фикстуры.
Подключать его как настоящий backend verifier без проверки прав, состояния
и полноты реального хранилища нельзя. [Тесты границы](tests/test_server_handoff.py)
показывают отказ до провайдера при нарушении проверяемых фикстурных фактов.

## Охват и передача между этапами

Генератор поддерживает многие-ко-многим evidence. `EvidenceSelection` выбирает
доступные fragment_keys конкретных findings; рассмотренный/контекстный набор
сохраняется отдельно. Пустой requirements с объяснением — содержательный исход.
Необработанные findings не поддерживают кандидата. Частичность внутри одного
finding текущий сервис отклоняет как `partial_scope_unverifiable`; отдельные
completed/insufficient_information/not_processed findings допускаются вместе.

Перед verify приложение сохраняет неизменяемую редакцию и разрешает local_id
генерации в настоящую идентичность Requirement/Revision. EvidenceSelection
преобразуется в RevisionEvidence с **теми же выбранными состояниями** и links;
это работа будущего backend, не автоматическая функция генератора. Рассмотренный
контекст, охват, вопросы и происхождение сохраняются отдельно от текста редакции.

Проверка выдаёт support/contradictions/ambiguity/duplicates, каждую один раз.
Issues имеют category, severity, blocking, blocking_reason, related, question_ids.
`completed` означает завершённое рассмотрение, а не чистый результат или Approved.
`not_processed` допускает только пустые considered, четыре inconclusive и пустые
issues. Недостаток информации и пропущенная работа различаются.

`partially_processed` требует отдельного [ReviewPlan](verify_requirement/validation.py)
независимого исполнителя: завершённые именованные оценки и comparison_keys.
План не строится из ответа модели и не входит в AI JSON. Он проверяется при
приёме ответа; приложение подготавливает и проверяет его до запуска.
Один Ollama-вызов не реализует пакетный исполнитель/агрегатор. Частичное чтение
текста этот план не доказывает. Полностью рассмотренный selected не становится
partial из-за ограничения области. Найденные независимые issues при частичном
охвате сохраняются, но пропущенные comparisons запрещают чистый вывод duplicates.

## Ошибки и ответственность исполнителя

Ошибки библиотек — `GenerationError`/`VerificationError` с безопасными `code`
и `rule`. Это не HTTP-статусы и не новые состояния Requirement.

| code / пример rule | Значение | Действие будущего приложения |
|---|---|---|
| invalid_request / schema, json_*, context_not_verified | Невалидный снимок или доверенная проверка отклонена | Не вызывать модель; исправить/пересобрать вход с явной привязкой, не подставлять новые states молча |
| configuration_error | Ошибка локальной схемы или служебной метаинформации | Остановить попытку, исправить конфигурацию; не выдавать содержательный результат |
| timeout / provider_timeout | Ответ не получен в срок | Записать технический исход без coverage; повтором управляет приложение |
| provider_error / provider_not_configured, provider_transport, provider_failure | Gate выключен, транспорт или адаптер недоступны | Не подменять ошибку пустыми кандидатами/чистыми checks; не раскрывать URL/сырой текст |
| invalid_response / schema, json_*, provider_envelope и прикладные rules | Ответ или транспортная оболочка не прошли приём | Отклонить весь ответ; не ремонтировать, не удалять невалидные части ради PASS |

Автоматического retry, хранения, публикации, lease или отмены в этих сервисах нет.
`cancelled` — ответственность вызывающего исполнителя по существующей технической
оболочке; нового метода отмены не введено. Технический повтор, повторное формирование
и повторная содержательная проверка различаются. Независимые принятые результаты
не стираются. Логи содержат разрешённые коды/метаданные, не сырые материалы.

## Повторная проверка и оставшиеся зависимости

Перед публикацией приложение повторно, атомарно с приёмом, проверяет права,
активность попытки, точные входы и их доступность, полный comparison snapshot,
историю и актуальность цели (AP-11–14). Inference выполняется вне блокировок.
Гонку после callback библиотека не предотвращает. Неизвестный исход COMMIT
требует чтения сохранённого состояния и идемпотентного приёма без слепой новой
генерации. Поздний ответ не восстанавливает удалённые данные.

Новые пустые issues не закрывают прежний блокер. Severity не задаёт blocking.
Новое Approved принимает только уполномоченный человек по точной редакции,
после проверки доступных пригодных оснований и всех существенных открытых вопросов.
Человеческие решения/редакции и прежнее Approved не переносятся автоматически.

Нужны отдельно согласованные серверные сборка снимков, хранение требований/
проверок/решений и подключение к исполнителю. Конкретный существующий проект
этого этапа — [PROPOSED пакет B](../docs/proposals/workflow-contracts.md#b-требования-редакции-и-проверки-минимальный-серверный-срез),
дополнительные условия — [verification handoff](../docs/proposals/verification-backend-handoff.md).
Их статус этим отчётом не меняется; новые endpoints/таблицы здесь не предлагаются.

Для runtime нужны Python 3.12, [зависимости AI](requirements.txt), пакет ai с
общим grouping transport/validation и локальные schemas по исходному пути
`docs/contracts/ai/v1/`. Runtime не зависит от evaluator, backend, Z3 или БД.
Нужны отдельные PG/API/гонки/lease/удаление/unknown-COMMIT проверки будущего backend.

Реальный провайдер/model и передача данных не разрешены этой работой.
Ollama gate остаётся выключенным по умолчанию; реальные inference, поддержка
диалекта схемы, лимиты контекста, injection и смысловое качество требуют отдельного
разрешения и экспертного эксперимента. Синтетический PASS этого не подтверждает.
