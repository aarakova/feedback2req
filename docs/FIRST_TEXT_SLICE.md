# Технический проект первого текстового среза

**PROPOSED / на согласование, ревизия 1 от 2026-10-21.**
DEC-006 утверждает стек, но не этот проект, физическую схему, endpoints или
механизм синхронизации. Здесь предлагается реализация DEC-001–DEC-006 без
изменения предметной модели и [AI-контрактов 1.0](AI_CONTRACTS.md).
DEC-007 отдельно утверждает и разрешает реализацию только И1: identity/projects,
M01, их HTTP-контрактов и защиты. Весь документ сохраняет PROPOSED; остальные
миграции, endpoints, worker и механизм §5 не утверждены этим разрешением.

## 1. Результат и границы

Первый полезный результат: регистрация → проект → сохранение русского текста
→ явный запуск → находки с точными цитатами. Затем небольшими задачами
добавляются группировка, кандидаты требований, проверка и решение человека.
Все этапы используют настоящую PostgreSQL и проектные права.

Срез принимает введённый текст отзыва и необязательный введённый текст
документа продукта. Один источник может дать несколько независимых сегментов;
для первого короткого отзыва используется один сегмент. Поддерживается запуск
по нескольким источникам, чтобы проверять сохранение независимого результата.
Текст сохраняется без изменения Unicode, пробелов и переводов строк;
пустой/пробельный ввод отклоняется. Размеры запросов ограничиваются конфигурацией;
конкретный эксплуатационный предел не объявляется новым продуктовым требованием.

Первый инженерный контур использует только фиктивные материалы и явно выбранный
mock. Его режим показывается у запуска и каждого результата. Нет скрытого
fallback на mock. Проверка решения на тестовых требованиях допустима; результаты
mock не используются для решений по реальным требованиям. Признак режима
сохраняется приложением в проекте и происхождении результатов, а не в AI DTO.

Аудио, видео, ASR, загрузка/разбор файлов, дашборды и расширенный workflow
уточнений следуют после начального сценария и остаются частью MVP в утверждённом
объёме. Общая система приглашений, восстановления пароля, SSO, RLS, брокер,
универсальный граф и пакетная проверка больших контекстов для старта не нужны.
Открытые вопросы/блокеры сохраняются; неподдержанный путь их закрытия не
имитируется. Это ограничение первого среза, а не отмена функций MVP.

## 2. Процессы и границы модулей

Compose запускает PostgreSQL, API и один worker. API раздаёт сборку React;
при разработке Vite проксирует `/api` к API. PostgreSQL использует постоянный
volume. Закрытый файловый volume предусмотрен утверждённым стеком, но введённый
текст хранится в БД: второй копии в файле первый сценарий не требует.
Конфигурация и секреты передаются окружением; репозиторий их не содержит.

| Модуль общего backend | Ответственность и взаимодействие |
|---|---|
| `identity`, `projects` | Учётные записи, серверные сессии, членство, право Approver, общая проверка проектного доступа. |
| `materials` | Тексты, состояния документов, подготовка сегментов, чтение оснований, удаление и очистка. |
| `analysis` | Приём и хранение фрагментов, находок, групп и человеческих исправлений. |
| `requirements` | Неизменяемые редакции, предложения, замечания, условия и история человеческих решений. |
| `processing` | Координатор, план зависимостей, сохраняемые задания, попытки, ручные повторы и технические исходы. Не решает предметные вопросы. |
| `ai_contracts`, `adapters` | Локальный реестр существующих схем, сборка канонических запросов, сменный mock/реальный адаптер. Адаптер не пишет в предметные таблицы. |
| `persistence`, `storage`, `api` | SQLAlchemy Unit of Work и репозитории, закрытые файлы, HTTP DTO/авторизация и представления. |

Предлагаемая структура: общий пакет `backend/feedback2req/`, миграции
`backend/migrations/`, React в `frontend/`. Это план будущих каталогов.
Два entrypoint используют одни прикладные сервисы и правила транзакций.
HTTP-обработчик вызывает сервис; worker вызывает координатор → сборщик входа
→ адаптер → прикладной приём → репозиторий. Роли AI друг друга не вызывают.
Программные проверки принадлежат прикладным модулям, не новой AI-роли.

## 3. Предлагаемая физическая модель и миграции

### 3.1 Общие правила

- Идентичности и `state_id` — UUID, созданные приложением. Исправляемый объект
  имеет заголовок с текущим указателем и отдельные содержательные состояния;
  у неизменяемой записи её UUID может одновременно служить `state_id`.
  Текстовый хэш не заменяет идентичность и историю.
- Время — `timestamptz` в UTC. Каждая проектная таблица содержит `project_id`.
  Ссылки на предметные записи — составные FK `(project_id, id)` на UNIQUE-пару;
  ссылки на состояния дополнительно проверяют принадлежность состоянию объекта.
  Указатели заголовков замыкаются FK на собственные состояния, не на чужой объект.
- Строковые технические состояния ограничены CHECK, связи — FK/UNIQUE/NOT NULL.
  Сложные правила приёма и Approved выполняет один прикладной сервис транзакции.
  Пользователь и модель не пишут напрямую в БД. Каскады удаления проекта не
  затрагивают глобального User.
- Текст и сущностные связи хранятся в отдельных колонках/таблицах. JSONB допустим
  для оценок, конфликтующих позиций и сообщений AI со структурой 1.0 после
  проверки; JSONB не является единственным хранилищем путей к основаниям.
- У содержательного состояния сохраняются автор, время, происхождение
  `ai|human|ai_and_human`, предыдущий state при исправлении и attempt при AI.
  Технический режим `mock|real` наследуется по происхождению. Текущий указатель
  не передвигается AI поверх человеческой правки без явного выбора человека.

### 3.2 Состав таблиц по мере появления функций

Это перечень минимально нужных групп, не одна начальная миграция на весь MVP.
Суффикс `*_states` означает отдельную таблицу состояний указанного типа.

| Группа таблиц | Основные поля и связи |
|---|---|
| `users`, `sessions` | User: `id`, уникальный нормализованный `login`, `password_hash`, время создания. Session: `token_hash`, `user_id`, CSRF-секрет, сроки действия, отзыв; сырой session token не хранится. |
| `projects`, `project_access` | Project: `id`, `owner_id`, название, `execution_mode`. Access: `project_id,user_id` PK, `can_approve`; членство следует из строки. Владелец получает Member/Approver по правилу, а не через отзывную запись доступа. |
| `feedback_sources`, `source_text_states` | Source: `id`, проект, вид `text`, текущий state, доступность. State: `id`, `source_id`, исходный `text`. Заголовок удалённого источника сводится к техническому ID и факту удаления внутри проекта. |
| `product_documents`, `document_states` | Заголовок и текущий state; состояние содержит текст, название, автора и время. Это контекст, не основание потребности. |
| `processing_runs`, `processing_units` | Run: инициатор, режим, запрошенные этапы/область, повторяемая клиентская команда. Unit: run, этап, независимая единица/ветвь, ожидаемые входы, зависимости на предшествующие units, текущее выполнение. Unit одновременно является сохраняемым заданием, второй очереди нет. |
| `stage_attempts`, `attempt_inputs`, `attempt_coverage` | Attempt: unit, номер, уникальные `request_id` и токен владения, lease/deadline, начало/конец, технический исход, код ошибки, факт публикации. Inputs: точные разрешённые refs, роли сравнения, ожидаемые указатели. Coverage: запрошенная/рассмотренная/пригодная/ненадёжная/ошибочная/ожидающая область. |
| `feedback_fragments`, `fragment_states` | Заголовок с текущим state; состояние: source/text state, цитата, `[start,end)`, надёжность, происхождение. Для текста времени записи нет. |
| `findings`, `finding_states`, `finding_evidence` | Состояние находки: текст, типы, direct/inferred, неопределённость, охват; evidence связывает точные состояния находки и фрагмента. Возможны многие-ко-многим. |
| `finding_groups`, `group_states`, `group_members` | Состояние группы: название, summary, конфликтующие позиции и охват; members ссылаются на конкретные состояния находок. Находка может быть в нескольких группах. |
| `requirements`, `requirement_revisions`, `revision_evidence`, `revision_context` | Requirement: текущая рассматриваемая и действующая утверждённая редакции, последнее относящееся решение. Revision: номер в пределах Requirement, title/text/rationale, авторство, охват. Evidence хранит выбранные finding state и конкретные пути к fragment state; context — document/group state отдельно. |
| `change_proposals`, `proposal_states` | Requirement, базовая утверждённая редакция, кандидатная редакция, автор, причина, состояние рассмотрения. История указателей/решения различима. Частичный UNIQUE по Requirement для незавершённого предложения. |
| `verification_results`, `verification_issues`, `issue_resolutions` | Проверка: точная revision, attempt, входные refs, manifest сравнения и четыре оценки. Issue: собственный ID, category/severity/blocking, причина, связи. Resolution: одно явное разрешение конкретного issue, способ, обоснование, автор; при исправлении — ссылка на проверку затронутого вывода. |
| `open_questions`, `question_targets` | Техническое хранение вопросов из принятых ответов: текст, причина, blocking, происхождение; типизированные ссылки на затронутые finding/group/revision/unit. Старые вопросы не закрываются новым AI-ответом. В первом срезе показываются открытыми; общий процесс ответов откладывается. |
| `human_decisions`, `decision_basis` | Автор, точная revision, решение, проверка, proposal при наличии; basis фиксирует рассмотренные состояния оснований, замечаний/разрешений и вопросов. Удаляемые исходные связи хранятся отдельно от неизменяемого факта решения. |

`attempt_inputs` и зависимости содержат типизированные колонки/FK для применимых
источников, документов, находок, групп, редакций, проверок и решений с CHECK
допустимых комбинаций; они не вводят универсальную предметную сущность/граф.
Manifest сравнений — набор revision/proposal refs с ролями, а не только хэш.
У охвата и контекстных связей результата есть собственные типизированные строки
для рассмотренных входов; выбранные evidence-строки не заменяют этот охват.
Эти дочерние таблицы добавляются вместе с соответствующим результатом.
Сырые полные AI request/response в БД, логи и очередь не сохраняются.

Сериализованный review context не архивируется в командах/диагностике. Если
для идемпотентности хранится отпечаток команды с review_token, при удалении
источника он также стирается; вместо повтора удалённого контекста возвращается
конфликт с предложением заново открыть карточку. Факт прежнего решения остаётся.

### 3.3 Инварианты хранения

1. UNIQUE `(requirement_id, revision_number)`; сохранённый revision не обновляет
   title/text/rationale и выбранный набор. Правка создаёт новую запись.
   Семантическая неизменяемость не запрещает предусмотренное удаление исходных
   данных: стирание деталей доступа описано ниже и не создаёт новую редакцию.
2. При создании finding нужен fragment; при создании revision — поддерживающий
   finding с выбранным путём к отзыву. Наличие document это условие не выполняет.
3. Один unit имеет не более одной активной попытки (частичный UNIQUE).
   Для одного attempt предметная публикация возможна один раз; принятые объекты
   имеют UNIQUE `(attempt_id, local_id)` в области соответствующего ответа.
   Для verification — UNIQUE attempt. UUID приложения назначаются лишь при приёме.
   У retry-unit есть `retry_of_attempt_id` с UNIQUE: у потерянной/ошибочной
   попытки один технический преемник. Повтор очередного сбоя ссылается уже на
   новую ошибочную попытку; два конкурентных retry не образуют две ветви.
4. Решение ссылается на точные revision/check. Действующую Approved-редакцию
   меняет только транзакция человеческого решения по проверенному предложению.
5. Индексы: проектные списки; очередные units по состоянию и времени;
   активные attempts по lease/deadline; обратные зависимости и пути evidence;
   issues/questions по затронутой редакции и открытому состоянию.

### 3.4 Удаление без обхода через историю

При удалении source в одной защищённой транзакции прекращается доступ,
удаляются все source text/fragment states и их координаты/цитаты, из **всех**
evidence, scope, attempt inputs/coverage, review context и decision basis
стираются source state, segment/fragment ID/state, позиции, время и хэши.
Их представление утраты содержит лишь `source_id` и факт удаления; несколько
фрагментов одного источника сворачиваются в одну отметку внутри основания.
Нельзя оставлять удалённые идентификаторы в JSONB или ссылках на прошлые состояния.
Разрешённые производные пересказы/цитаты в находках и требованиях сохраняются.

Стиранию подлежат отдельно хранимые детали доступа, а не формулировка revision
или факт HumanDecision. Выбранное основание проецируется как утраченное согласно
разделу 5 AI_CONTRACTS; новые состояния вместо старых не подставляются.
Зависимости помечаются требующими актуализации, прежнее Approved сохраняется.
Старые задания отменяются/теряют право публикации. При удалении проекта
удаляются все его предметные и технические строки; старый worker видит отсутствие
проекта и не создаёт его заново. Пользователь остаётся.

В текстовом срезе нет файловых копий исходного ввода. Для последующих файлов
нужна сохраняемая запись очистки и повторяемый unlink, недоступность материала
наступает до физической очистки; это не реализуется заранее. Историческая связь
не хранит путь к файлу. Сроки очистки временных данных и резервных копий,
условия провайдера остаются эксплуатационными вопросами; этот проект не обещает
их полного удаления. Временный AI DTO живёт только в памяти ограниченного
вызова и после отмены/таймаута не сохраняется и не используется повторно.

### 3.5 Предлагаемые пакеты Alembic

| Пакет | Содержание | Проверяемый результат |
|---|---|---|
| M01 | users/sessions/projects/access | Пустая БД поднимается миграцией; регистрация и проект сохраняются после перезапуска. |
| M02 | source/document states, runs/units/attempts/inputs/coverage | Введённый текст и очередь переживают перезапуск; таблицы аудио не создаются. |
| M03 | fragments/findings/evidence и их scope/context | По находке открывается точное сохранённое основание. |
| M04 | groups/members, requirements/revisions/evidence/context | Сохраняются группы и кандидаты, правка даёт новую revision. |
| M05 | verification/issues/resolutions/questions, proposals, decisions/basis | Проверка и решение воспроизводимы, ограничения предложения защищены. |

Входные FK дополняются вместе с появлением таблиц. Каждый пакет проверяется
на чистой БД и обновлении с предыдущего; проверки rollback допустимы только
на отдельной тестовой БД. Рабочие данные миграциями не сбрасываются.
DDL и файлы Alembic создаются после согласования, по одному пакету к задаче.

## 4. Предлагаемый HTTP API

Префикс `/api/v1`, JSON UTF-8; неизвестные поля отклоняются. UUID объектов
приложения передаются строками. Это внешний контракт, он не копирует оболочку
AI-запроса. `p` ниже означает `/api/v1/projects/{project_id}`.
Ответы со списками имеют `{items, next_cursor}`; лимит задаётся сервером.

| Метод и путь | Вход → результат | Доступ |
|---|---|---|
| `POST /auth/register` | `{login,password}` → `201 {id,login}`; сессия отдельным входом | Без сессии |
| `POST /auth/session` | `{login,password}` → `200 {user,csrf_token}`, cookie | Без сессии |
| `GET /auth/session` | Текущий пользователь и CSRF token, либо 401 | Сессия |
| `DELETE /auth/session` | Отзыв сессии, очистка cookie → 204 | Сессия + CSRF |
| `POST /projects`, `GET /projects` | `{name}` → `201 Project`; список доступных проектов | User |
| `GET p`, `PATCH p` | Project с текущими правами; изменение `{name}` → 200 | Member / Owner для PATCH |
| `GET p/access`, `PUT p/access/{user_id}`, `DELETE p/access/{user_id}` | Участники; `{can_approve}` добавляет/меняет доступ зарегистрированного User; удалить доступ → 204 | Owner |
| `POST p/sources`, `GET p/sources`, `GET p/sources/{id}` | `{kind:"text",text}` → `201 {id,state_id,kind,text}`; чтение доступного текста | Member |
| `POST p/documents`, `GET p/documents`, `GET p/documents/{id}` | `{title,text}` → `201 {id,state_id,title,text}`; контекст продукта | Member |
| `POST p/documents/{id}/states` | `{expected_state_id,title,text}` → 201 новое состояние; зависимые результаты требуют актуализации | Member |
| `POST p/runs`, `GET p/runs/{id}` | Область/этапы → 202 Run; GET показывает units, attempts, охват, ошибки и результат | Member |
| `POST p/units/{id}/retries` | `{expected_attempt_id}` → 202 новый retry run с новой попыткой ошибочного этапа | Member |
| `GET p/findings`, `GET p/findings/{id}` | Текущий state, авторство, неопределённость, evidence и охват | Member |
| `GET p/fragments/{id}/states/{state_id}` | Точная цитата, source/text refs и Unicode locator доступного состояния | Member |
| `POST p/findings/{id}/states` | `{expected_state_id,text,types,mode}` → 201 человеческий state; прежние состояния остаются | Member |
| `GET p/groups`, `POST p/groups/{id}/states` | Просмотр; `{expected_state_id,title,summary,finding_state_ids,conflicts}` → 201 исправление | Member |
| `GET p/requirements`, `GET p/requirements/{id}` | Редакции, действующая редакция/решение, проверки, открытые препятствия, evidence и охват раздельно | Member |
| `POST p/requirements/{id}/revisions` | `{expected_revision_id,title,text,rationale,evidence}` → 201 revision неутверждённого требования | Member |
| `POST p/requirements/{id}/proposals` | `{base_revision_id,title,text,rationale,evidence,reason}` → 201 предложение изменения Approved | Member |
| `POST p/proposals/{id}/revisions` | Те же содержательные поля + `expected_proposal_state_id` → 201, новый state предложения | Member |
| `GET p/requirements/{id}/review-context` | Проверяемый комплект для решения, точные refs и `review_token` | Member |
| `POST p/requirements/{id}/decisions` | Точная revision/check, действие, review_token, proposal при наличии → 201 HumanDecision | Approver |
| `POST p/issues/{id}/resolutions` | `{kind:"not_applicable",reason,expected_issue_state_id}` → 201 мотивированное разрешение | Approver |
| `GET p/sources/{id}/deletion-preview`, `DELETE p/sources/{id}` | Предупреждение/область; `{confirmation_token}` → 204 после удаления текста и очистки ссылок | Owner |
| `GET p/deletion-preview`, `DELETE p` | Предупреждение/область; `{confirmation_token}` → 204 удаление данных проекта | Owner |

UI получает User.id из профиля; глобального каталога пользователей первый
срез не предоставляет. Owner добавляет участника по известному User.id.
Владелец не может лишить себя полномочий через access endpoint.
Произвольная замена evidence в Finding не входит в первую форму исправления.
Изменение текста/классификации всё равно образует новый state.
Для исправления причины замечания последующая целевая проверка сохраняется
через `followup`; автоматического закрытия старого issue нет. Общий UI
такого разрешения добавляется позднее, право не расширяется этим проектом.

### 4.1 Запуск, повтор и чтение результата

Первоначальная команда запуска (пример, не внутренний AI DTO):

```json
{"source_ids":["<uuid>"],"document_state_ids":[],"through":"extract_feedback"}
```

`through` ограничен `extract_feedback|group_findings|generate_requirements|verify_requirement`.
Для продолжения уже принятого результата используется альтернативная закрытая
форма `{from_run_id, through}`; для повторной проверки —
`{revision_id, document_state_ids, followup?}`. Формы не смешиваются.
`followup` содержит previous_result_id и issue_ids того же проекта/требования.
Новый запуск захватывает текущие состояния; технический retry разрешён только
при неизменных входах. Иначе 409 с требованием явно начать новый анализ/проверку.
Успешные предшественники не переисполняются, их точные выходы становятся входами
продолжения. Для генерации уже сформированных кандидатов требуется отдельный
явный запуск, новые кандидаты не заменяют прежние или человеческую редакцию.

`Idempotency-Key` обязателен для запуска, retry и решения; ключ уникален
в пределах пользователя/проекта/операции, одинаковый повтор возвращает прежний
результат, другое тело с тем же ключом даёт 409. Ключ сохраняется в run/decision
без отдельного сервиса. Для решения различается ещё и повтор команды после
утраты прав: доступ проверяется заново даже для чтения прежнего ответа.

Run показывает `{id, execution_mode, execution_state, units, result_ids}`.
Unit различает техническое выполнение, состояние приёма, фактический coverage,
неопределённость и актуальность; UI не выводит общий «AI подтвердил».
Карточка требования содержит `current_revision`, `approved_revision`,
`human_decision`, `verification`, `basis_availability`, `freshness`,
`open_issues`, `open_questions`, `considered_scope`, `evidence`.
Evidence передаётся как доступная выбранная связь с refs/locator либо
`{kind:"deleted_source",source_id}` без деталей удалённого фрагмента.
Содержимое состояний получается по точным refs; новое состояние не подменяет
то, которое выбрали для редакции. Листинг использует те же отдельные признаки.

### 4.2 Решение, предусловия и ошибки

Revision evidence во внешней команде — массив
`{finding_state_id,fragment_state_ids:[...]}`. Все связи проверяются сервером.
В решение передаются `{revision_id,verification_result_id,action,review_token}`,
где `action=approve|reject`; для предложения дополнительно `proposal_id`.
`review_token` — выданный сервером непрозрачный подписанный комплект/отпечаток
точных refs редакции, оснований, проверки, открытых препятствий и предложения.
Он не даёт права решения и не содержит исходного текста. Сервер пересчитывает
комплект под блокировкой; один актуальный revision_id недостаточен.
Для reject поле проверки может отсутствовать: не вводится новое обязательное
условие проверки для отклонения неутверждённого кандидата.

В транзакции Approved заново проверяются сессия, Approver, нужная редакция,
её проверка и актуальность входов/сравнения, доступное пригодное основание,
старые открытые блокеры и существенные вопросы, текущее предложение/решение.
Смысловая достаточность не выводится из числа ссылок. В UI до отправки решения
видны основания и содержательные оценки; окончательный выбор делает Approver.
Неполный охват сам по себе не запрещает Approved при соблюдении утверждённых
условий. Исчезновение issue из новой проверки не закрывает прежний блокер.

Ошибка имеет форму `{error:{code,message,details,request_id}}`; details не
раскрывает чужих или удалённых материалов. 401 — нет действующей сессии;
404 — нет доступного проекта/объекта, включая чужой ID; 403 — участнику не
хватает полномочий; 422 — неверная структура/ссылки собственной команды;
409 — устаревшие refs, изменённый review context, активная попытка,
недопустимый повтор/решение, открытое предложение или конфликт Idempotency-Key.
Ошибки фонового AI появляются в Run, а не превращаются в HTTP 500 после 202.
Слишком большой HTTP body даёт 413, ограничение частоты входа — 429.
Confirmation token удаления связывает объект, текущий состав и пользователя;
при изменении области требуется новое предупреждение. Это отдельный token,
не review_token. GET не меняет предметные данные и не запускает AI.

## 5. Фоновый запуск и защита публикации

### 5.1 Минимальная очередь

Один worker последовательно исполняет units, опрашивая PostgreSQL. В транзакции
запуска сохраняются Run и начальные units. Захват queued-unit и создание attempt
происходят атомарно (`FOR UPDATE`, допустимо `SKIP LOCKED`). Приём предметного
выхода, завершение attempt и создание готовых зависимых units коммитятся вместе:
сбой между этапами не теряет продолжение. Успешные независимые units не откатываются.

Техническое выполнение unit: `waiting → queued → running → completed|failed|cancelled`.
`waiting` означает ожидание зависимостей. У attempt отдельно исход транспорта
`returned|failed`, приём `accepted|rejected|not_attempted`, причина и актуальность.
Устаревший returned-ответ не становится предметным выходом; cancellation reason
объясняет отсутствие публикации. Техническая ошибка имеет один из кодов
`timeout|provider_error|invalid_response|cancelled`, детализация не содержит DTO.
Run агрегирует выполнение и показывает пробелы, а не заменяет coverage одним статусом.

Невалидный ответ завершает unit как failed с `invalid_response`, приёмом rejected;
устаревший/отменённый — как cancelled с причиной, приёмом rejected либо
not_attempted. Валидное отсутствие находок завершает unit как completed/accepted.
Приём всех объектов ответа одной единицы атомарен, отдельные units независимы.

Worker владеет attempt по случайному токену, периодически продлевает lease
коротким условным UPDATE и соблюдает абсолютный deadline вызова. Lease и deadline
проверяются по времени БД. Heartbeat выполняется отдельно от ожидающего AI-вызова;
он не может продлить абсолютный deadline. Только queued-units берутся заново.
Незавершённые attempts с истёкшим lease/deadline при старте и в цикле worker
атомарно помечаются failed (`timeout`, detail `attempt_lost` либо `deadline_exceeded`),
токен отзывается. Неистёкшая старая попытка ожидает своего срока; старт нового
процесса сам по себе не доказывает её потерю. Автоматических повторных AI-вызовов нет.

Ручной retry создаёт новый Run/attempt/request_id с ссылкой на старую попытку,
проверяет текущие права и входы. Поздний ответ старого процесса отклоняется по
отозванному токену/lease, даже если его входы не изменились. При потере связи
после COMMIT worker перечитывает запись публикации, а не публикует повторно.
Защищается однократная публикация в БД; однократность внешнего платного вызова
при сетевом сбое не обещается. Параллельные повторы одной ошибки защищены
UNIQUE/условным переходом, повтор Idempotency-Key возвращает тот же Run.

Если понадобятся несколько worker, приоритеты, сложные расписания, автоматические
ретраи или распределённое владение, сначала отдельно сравниваются текущая очередь
и готовое минимальное решение. Сейчас такие механизмы не добавляются.

### 5.2 Самый простой предлагаемый механизм конкурентности

Рассмотрены CAS по всем объектам, SERIALIZABLE с повторами транзакций и короткая
блокировка строки Project. Предлагается последняя: маленькая нагрузка и единый
backend позволяют централизовать правило без счётчиков всех видов изменений.
Это выбор **проекта ревизии 1**, а не обязательство, уже установленное DEC-006.

Все изменения материалов, выбранных текущих состояний, кандидатов, предложений,
прав доступа, вопросов/замечаний и решений получают `SELECT Project FOR UPDATE`
в начале короткой транзакции READ COMMITTED. Затем читаются текущие данные.
Захват/отзыв attempt и публикация используют тот же порядок: Project → unit → attempt.
Обычные чтения не требуют этой блокировки. HTTP-сервис и worker используют
один транзакционный helper; обходной путь записи запрещён соглашением модулей.

1. Под короткой блокировкой фиксируются разрешённые входные refs, выбранные
   состояния и полный manifest сравнения. Канонический DTO собирается из этих
   данных; транзакция завершается до AI-вызова. Недоступный при сборке вход
   отменяет вызов. Для больших файлов IO также выносится за пределы блокировки.
2. Адаптер вызывается без открытой транзакции/блокировок. Ответ проверяется
   локально по схемам и связям запроса, но ещё не является текущим результатом.
3. Новая короткая транзакция вновь блокирует Project, проверяет существование,
   текущие права инициатора, владение/срок attempt, состояния входов, человеческие
   правки, выбранные указатели и **весь состав/роли** comparison manifest.
   Если сохранённое состояние ещё существует, но уже не текущее, это не успех.
4. При совпадении принимаются все объекты одной атомарной единицы, назначаются
   IDs, сохраняются связи/охват, отметка публикации и продолжение. При расхождении
   предметные объекты не публикуются; UI показывает причину и возможность нового
   явного запуска. Незатронутые принятые результаты остаются.

Повторная проверка manifest защищает от нового требования и изменения указателя
предложения, даже если прежние comparison state_id не изменились. Короткая
блокировка сериализует writers, а refs определяют затронутость: изменение
независимого источника не делает все результаты проекта устаревшими.
После нового кандидата/решения уже сохранённые проверки с затронутым составом
сравнения получают отметку актуализации. При невозможности точно ограничить
влияние помечается соответствующая зависимая ветвь, без автоматического AI-вызова.

Тот же механизм защищает HumanDecision: права и весь review context читаются
повторно и проверяются в транзакции, которая сохраняет решение и действующий
указатель. Два разных решения по одному рассмотренному состоянию не могут
оба незаметно пройти. Удаление, если оно коммитится раньше публикации, исключает
публикацию; если позже — очищает уже принятый результат по утверждённым правилам.

Основание технического выбора — [PostgreSQL: Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html).
Блокировка строки сама по себе не защищает от writers, которые не соблюдают
протокол; поэтому необходимы общая точка записи и интеграционные проверки гонок.

## 6. Прикладной приём AI-результатов

Основной источник — AI_CONTRACTS.md, раздел 9 (AP-01–AP-14). Существующий
скрипт проверки примеров не становится runtime-валидатором БД. Предлагается
использовать jsonschema Draft 2020-12 с локальным registry уже утверждённых
схем. Pydantic допустим для внешнего HTTP API, не для второго канонического
AI-контракта. Адаптер может менять транспорт провайдера, но не ослаблять приём.

| Момент/ответственный модуль | Обязательная прикладная проверка |
|---|---|
| Сборка контекста: identity/projects + processing | AP-01–AP-03, AP-14: доступ, один проект, точные refs, ключи, prior_decision/change_context/followup. Схема проверяет и запрос. |
| Чистый валидатор: ai_contracts + analysis | AP-02, AP-04–AP-08: локальные ссылки, точная цитата/occurrence с перекрытиями, Unicode code points, наследование reliability, evidence, coverage, состав групп и позиций. |
| Приём verification: requirements | AP-09–AP-10: весь comparison manifest, четыре вида checks, связанные issues/questions, different Requirement.id для дубля, согласованность вывода с фактическим рассмотрением. |
| Публикация: общий прикладной сервис | AP-03, AP-11, AP-13: живые состояния, проект, доступ, токен попытки, отсутствие удаления, атомарная публикация/дедупликация. |
| Решение/разрешения: requirements | AP-12, AP-14: точная revision/check, старые открытые препятствия, явное мотивированное разрешение, Approver, отсутствие наследования решения. |

Один segment — один extract-запрос. Любой частичный extract отклоняется целиком,
принятые другие сегменты сохраняются. Для короткого текста не вводится скрытый
чанкинг моделью. При превышении контекста сегменты готовит приложение, сохраняя
точные исходные диапазоны; неподдержанный объём даёт явную ошибку, не усечение.
Группировка применяется к выбранному пригодному набору (в первоначальном
workflow — при двух и более находках); при одной находке groups пуст.
Каждая обработанная находка находится в группе либо явно остаётся отдельно.
Генерация сохраняет кандидаты одной операции до проверки каждого из них,
поэтому manifest учитывает и других новых кандидатов этого запуска.

Пустые findings/requirements с корректными coverage и причиной — успешный
исход, без выдуманного кандидата и без технического retry. Невалидный ответ
не ремонтируется и не передаётся дальше. Проверка одной revision принимается
атомарно; большие пакетные агрегаты пока не реализуются. Если контекст не
помещается, показывается ограничение, а не ложный вывод об отсутствии дублей.

Вопросы и неопределённость сохраняются с областью влияния, старые препятствия
загружаются независимо от нового ответа. Детерминированные проверки не доказывают
смысловую поддержку, достаточность, фактическое чтение, правильность серьёзности
или существенности вопроса. За это отвечают содержательная проверка и человек.

## 7. Минимальная аутентификация и изоляция

Предлагается локальный login/password, Argon2id для пароля, случайный session
token в cookie `HttpOnly; SameSite=Lax; Path=/`; `Secure` обязателен при HTTPS.
Сырой token не хранится в БД/логах; срок и idle timeout проверяются сервером,
logout отзывает сессию. Вход выдаёт новую сессию, не сохраняет присланный session ID.
Параметры Argon2 и сроки выбираются/фиксируются конфигурацией при реализации.
Ошибки входа не раскрывают наличие пользователя; ввод и частота входов ограничены.

Все изменяющие запросы проверяют допустимый Origin; после входа нужен CSRF
token, включая logout. Анонимные register/login защищены проверкой Origin и
JSON content type. SameSite не заменяет CSRF-проверку. Для localhost допустим
HTTP только в локальном профиле; реальная работа в LAN использует TLS.
Источник решения — [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
и [CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

API проверяет доступ и объект внутри указанного project_id, не только знание UUID.
Репозитории принимают обязательный project_id; составные FK защищают от чужих
связей. Worker не имеет «пользовательского HTTP доступа»: он обрабатывает
сохранённое задание с проектной привязкой и заново проверяет права инициатора
до вызова и публикации. Отзыв прав не позволяет позднюю публикацию.
При чтении данных права актуальны; скрытая кнопка UI не считается защитой.
RLS не требуется для начала: достаточно общей точки доступа, FK и проверок.

## 8. Небольшие задачи и проверки результата

Каждая строка — отдельная проверяемая задача/изменение. M-пакеты добавляются
в соответствующем этапе; не требуется один PR на весь вертикальный срез.
Первые сквозные пути проверяются через HTTP; React добавляется по готовности
пути и не задерживает проверку реального сохранения.

| Этап | Изменение и наблюдаемый результат | Критерии/проверки |
|---|---|---|

После И9 — ASR/аудио/видео, файловая очистка и остальные функции MVP отдельными

AI-пороги не блокируют И1–И8; к соответствующей функции их нужно согласовать.

Минимальная валидация при реализации: unit-проверки чистых правил и ссылок;
интеграционные проверки на настоящей PostgreSQL для FK, миграций, restart,
lease, транзакций и конкурентных изменений; API-проверки ролей/изоляции/ошибок;
один браузерный сквозной путь с явно обозначенным mock. SQLite не заменяет
проверку транзакционного протокола PostgreSQL. Каждый тест связывается с
FR → AC, внутренним AP и наблюдаемым нарушением; качество естественного языка
проверяется экспертно, без требования точного совпадения формулировок.

Для И9 заранее нужен небольшой экспертно размеченный русскоязычный набор:
прямой/выведенный запрос, нет находок, неоднозначность, конфликт отзывов,
расхождение с документацией, неподдержанный вывод, дубль и собственная редакция,
частичная/полная утрата. Метрики и пороги согласуются отдельно до заявления
работоспособности AI; текущий документ не назначает модель или победителя.
