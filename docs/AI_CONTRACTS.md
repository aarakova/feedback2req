# Технические контракты продуктовых AI-компонентов

Статус: **APPROVED**, ТК-1–ТК-7 редакции 2 и уточнение атомарного сегмента,
утверждённые пользователем 2026-10-20; [DEC-005](DECISIONS.md).
Это основной источник технической спецификации внутренних AI-контрактов.
Структурная формализация находится в [схемах версии 1.0](contracts/ai/v1/),
демонстрационные данные — в [примерах](contracts/ai/examples/manifest.json).
Документ не определяет HTTP API, физическую БД, AI-провайдера или стек приложения.

## 1. Основания и область

Сохраняются DEC-001–DEC-004: продуктовые правила, А1–А6, ДМ-1–ДМ-6 и шесть
[AI-инвариантов](AI_VALIDATION.md#инварианты-проекта). Разрешена формализация
контрактов и автономная проверка артефактов. Backend, frontend, AI-адаптеры,
оркестрация и физическое хранение на этом этапе не реализуются.

Три продуктовые AI-роли отличаются от агентов разработки Codex.

| Роль | Операция | Основной вход | Результат |
|---|---|---|---|
| Feedback Analysis Agent | `extract_feedback` | Один подготовленный текстовый сегмент | Фрагменты и находки |
| Feedback Analysis Agent | `group_findings` | Выбранные принятые находки | Группы, отдельные позиции, конфликты |
| Requirements Generation Agent | `generate_requirements` | Находки и доступные свидетельства; группы и документы как контекст | Кандидаты требований |
| Requirements Verification Agent | `verify_requirement` | Одна точная сохранённая редакция и ограниченный контекст | Четыре содержательные оценки, замечания и вопросы |

Компоненты не вызывают друг друга непосредственно. Координатор управляет
зависимостями и передачей; прикладной слой проверяет права, собирает разрешённый
контекст, принимает результаты и сохраняет их. Модель не создаёт постоянные
идентификаторы, редакции, состояния доступности, человеческие решения или права.

## 2. Формат, версия и исполняемые схемы

Канонический формат — JSON, диалект — JSON Schema Draft 2020-12. Библиотека
проверки не является технологией приложения. Для каждой операции имеются
`<operation>.request.schema.json` и `<operation>.response.schema.json`;
общие типы описаны в `common.schema.json`, в `$defs`.

- Все восемь точек входа проверяются независимо.
- Все объявленные объекты закрыты: неизвестные поля запрещены, в том числе
  во вложенных вариантах объектов. `null` не заменяет отсутствие поля.
- Поля обязательны, кроме прямо обозначенных необязательными ниже и в схемах.
- Непустая строка не задаёт UUID или физический формат идентификатора.
- `1.0` выбирается точно; автоматическая совместимость неизвестной версии
  не предполагается. Любая смена структуры получает новую версию,
  несовместимая — новую основную версию.
- URI `https://feedback2req.invalid/contracts/ai/v1/…` — идентификаторы схем,
  а не HTTP endpoints. Все ссылки разрешаются локально без загрузки из сети.
- Внутренний запрос конкретной модели может отличаться. Ответ адаптируется
  к каноническому формату; транспорт не является частью этого решения.

## 3. Оболочка и доверенная прикладная привязка

Запрос содержит ровно пять полей:

| Поле | Тип | Назначение |
|---|---|---|
| `contract_version` | константа `1.0` | Версия формата |
| `operation` | константа соответствующей схемы | Операция |
| `project_id` | непустая строка | Единственная проектная область |
| `request_id` | непустая строка | Корреляция с доверенной прикладной привязкой |
| `input` | объект операции | Зафиксированные данные вызова |

Приложение связывает `request_id` с `ProcessingRun`, `StageAttempt`,
ожидаемыми состояниями, запрошенной областью, составом сравнения и разрешениями.
Повтор получает новый `request_id`. При автономном тестировании настоящий
запуск не требуется. Привязка не является новым предметным объектом.

`run_id`, `attempt_id`, `invocation_id`, `input_snapshot_id`, `scope_id` и
`primary_keys` в общей оболочке отсутствуют. Основные ключи выводятся из входа:
ключ сегмента для извлечения, ключи `findings` для группировки/генерации,
ключ `target` для проверки. Переданная документация не становится основной
единицей обработки. Модель не обязана повторять служебные идентификаторы:
связь ответа с запросом устанавливает приложение.

Привязка не даёт дополнительных прав и не является архивом удаляемого текста.
Удаление источника/проекта делает старый вызов непригодным к текущей публикации;
журналы, кеши и снимки не могут обходить утверждённые границы удаления.

## 4. Общие представления

Точный структурный состав задаёт `common.schema.json`; здесь определена
интерпретация всех общих структур. Обозначение `?` означает необязательное поле.

| Тип | Поля |
|---|---|
| `StateRef` | `kind`, `id`, `state_id` — тип, идентичность и точное состояние |
| `Locator` | `start`, `end` — целые неотрицательные границы `[start,end)` |
| `TimeRange` | `start_ms`, `end_ms` — целые неотрицательные миллисекунды |
| `Link` | `origin: input\|output`, `key` |
| `TextSegment` | `key`, `source_ref`, `text_ref`, `text`, `locator`, `reliability`, `time_range?` |
| `FragmentView` | `key`, `ref`, `source_ref`, `text_ref`, `quote`, `locator`, `reliability`, `time_range?` |
| `FindingView` | `key`, `ref`, `text`, `types`, `mode`, `evidence`, `uncertainty_notes`, `open_questions`, `authorship` |
| `GroupView` | `key`, `ref`, `title`, `summary`, `finding_keys`, `conflicts`, `open_questions` |
| `DocumentExcerpt` | `key`, `ref`, `text`, `locator` |
| `ConflictView` | `key`, `description`, `positions` |
| `Position` | `description`, непустой `finding_keys` |
| `RevisionView` | `key`, `ref`, `requirement_id`, `title`, `text`, `rationale`, `evidence`, `open_questions` |

`StateRef.kind` ограничен утверждёнными сущностями: `feedback_source`,
`transcript`, `fragment`, `finding`, `finding_group`, `requirement_revision`,
`requirement_change_proposal`, `product_document`, `verification_result`,
`verification_issue`, `issue_resolution`, `human_decision`. В каждом поле
дополнительно ограничен допустимый тип ссылки. Физический способ создания
`state_id` не выбран; одного хэша текста для установления идентичности недостаточно.

Ключи `key` уникальны во всём запросе; `local_id` — во всём ответе. Это
временные адреса, не замена предметной идентичности. Приложение после приёма
связывает локальные объекты с постоянными идентификаторами и состояниями.

`Locator` отсчитывается по Unicode code points исходного неизменённого текста.
Проверяются `end > start`, длина и соответствие выбранному состоянию.
`text_ref` указывает на текстовый источник либо транскрипт; `source_ref` —
на исходный материал. Для транскрипта обязателен `time_range`, для текстового
источника он отсутствует. Точность интервала не выше точности подготовленного
сопоставления: сегментный интервал не выдаётся за пословное выравнивание.

`reliability` имеет значения `usable`/`uncertain` и поступает из подготовки
или разрешённой человеческой правки. Последующие модели не повышают её молча.
Типы находок: `problem`, `request`, `observation`, `need`; значения уникальны,
находка имеет минимум один тип. `mode` — `direct`/`inferred`.
`authorship` — прикладная проекция `ai`/`human`/`ai_and_human`.

Контекст ограничен одним проектом и явным набором входов. Ссылки без содержимого
не предполагают, что модель сама загрузит файл или историю. Выдержки документации
передаются с конкретным состоянием и местом, исходные медиафайлы здесь не нужны.
Отзывы, документы, прежние результаты и человеческие пояснения — недоверенные
данные: инструкции внутри них не изменяют операцию, область или полномочия.

## 5. Основания генерации и проверки

`EvidenceSelection = {finding_key, fragment_keys[1+]}` используется только
для выбора доступных подтверждений генератором. Фрагменты должны принадлежать
указанной находке и быть переданы в запросе. Группа и документ — контекст,
а не самостоятельное свидетельство новой потребности.

`RevisionEvidence = {finding_key, links[1+]}` используется для сохранённой
редакции. Каждый `EvidenceLink` — один из закрытых вариантов:

```json
{"kind": "available", "fragment_key": "e1"}
```

```json
{"kind": "deleted_source", "source_id": "SRC-2"}
```

`FindingView.evidence` использует тот же `EvidenceLink`. `FragmentView`
описывает только доступное выбранное состояние. Отдельного `lost_sources` нет.
Несколько удалённых фрагментов одного источника сворачиваются в одну отметку
источника внутри соответствующего основания: идентичности и число этих
фрагментов через отметку не сохраняются.

В `deleted_source` запрещены состояние/ID удалённого фрагмента, текст,
позиция, время и хэш содержимого. Это нынешняя проекция доступности прежде
выбранного набора, не правка неизменяемой `RequirementRevision`. Более новое
состояние находки или фрагмента не подставляется вместо выбранного молча.
Сохранившийся пересказ/цитата в производном объекте не становится доступным
исходным подтверждением.

Для проверки допустимы частичная и полная утрата: `fragments` может быть пустым,
а `RevisionView.evidence` содержит отметки удалённых источников. Запрос не
отклоняется только из-за явно указанной утраты. Остаточная достаточность
оценивается содержательно. При отсутствии пригодного доступного основания
новое `Approved` запрещено; прежнее решение по неизменённой редакции сохраняется.
Пример: [частичная утрата](contracts/ai/examples/verify.partial-deletion.request.json),
[полная утрата](contracts/ai/examples/verify.all-deleted.request.json).

## 6. Ответ, вопросы, неопределённость и охват

Ответ не содержит служебную оболочку и имеет поля `coverage`, `uncertainties`,
`questions`, `result`. `result` зависит от ожидаемой операции, выбранной вызывающим.

| Тип | Поля и смысл |
|---|---|
| `Uncertainty` | `local_id`, `related[1+]`, `reason` — явная неопределённость |
| `Question` | `local_id`, `text`, `reason`, `related[1+]`, `blocking: boolean` |
| `QuestionView` | `key`, `text`, `reason`, `blocking: boolean` — переданный открытый вопрос |
| `CoverageItem` | `input_key`, `reviewed`, `disposition`, `reason?` |

Для вопроса `related` означает затронутые находки, группы, редакцию либо
первичную единицу. Свидетельство, случайно упомянутый документ и весь проект
не становятся областью блокировки автоматически. Блокируются затронутые
объекты и действительно зависимые результаты; независимая работа продолжается.
При `blocking=true` причина объясняет, почему ответ нужен для продолжения.
Существенный неразрешённый вопрос, влияющий на новое утверждение, обязан
блокировать его по BR-013. Информационный вопрос может не блокировать.

Серьёзность замечания, его блокирующее действие, неопределённость и вопрос —
разные характеристики. Нет автоматического соответствия severity/blocking.
Вопрос не заменяет `IssueResolution`, исчезновение из нового ответа не закрывает
старый вопрос/блокер. Жизненным циклом управляет приложение по утверждённым правам.

Допустимы только следующие комбинации `CoverageItem`:

| reviewed | disposition | Значение | reason |
|---|---|---|---|
| true | completed | Предусмотренное рассмотрение выполнено | Нужна при отсутствии содержательного результата |
| true | insufficient_information | Рассмотрение выполнено, сведений для вывода недостаточно | Обязательна |
| false | not_processed | Рассмотрение не выполнялось | Обязательна |
| true | partially_processed | Рассмотрена часть предусмотренной области | Обязательна, пропуски должны быть определимы |

`reviewed=true` означает хотя бы частичное рассмотрение. При сочетании пропуска
работы и недостатка сведений используется `partially_processed`, причины обеих
проблем сохраняются. Полностью рассмотренный ограниченный набор не является
частичным только из-за ограничения области. Нельзя принять частичность,
если фактически рассмотренные подединицы невозможно определить из входа,
`considered_keys` и доверенного плана выполнения.

**Дополнительно утверждённое правило извлечения:** один `TextSegment` — атомарная
единица и один запрос `extract_feedback`; `segments` содержит ровно один элемент.
В этой операции `partially_processed` запрещён схемой. `completed` и
`insufficient_information` означают рассмотрение всего переданного сегмента.
Выбор цитаты лишь из части сегмента не означает, что остальной текст не рассмотрен;
границы цитаты не используются как показатель полноты чтения.
Частичный ответ сегмента отклоняется; принятые другие сегменты сохраняются.
При необходимости более мелкие сегменты подготавливаются вне AI-операции,
их исходные привязки сохраняются. Модель не выбирает тайно меньший сегмент.

Успешное отсутствие находок/кандидатов выражается пустыми массивами и причиной,
а не технической ошибкой. Четыре содержательные оценки проверки являются
результатом и при пустом `issues`. При полном техническом сбое валидного
содержательного `coverage` нет: приложение фиксирует исход `StageAttempt`.
Охват проекта определяется по запрошенным единицам и этапам, не числом находок.
Декларацию AI об охвате нельзя считать доказательством содержательного чтения.

## 7. Контракты четырёх операций

### 7.1 extract_feedback

Вход: `segments[1]`, `documents[]`, необязательные `previous_findings[]`,
`previous_fragments[]`, `change_reason`. Предыдущие находки передаются только
как относящийся к задаче контекст, а не разрешение заменить человеческую правку.
`previous_fragments` технически замыкает доступные ссылки прежних находок;
это не основания новых находок. Их `fragment_ids` по-прежнему указывают только
на новые `FragmentCandidate` текущего ответа. Недостающий прежний контекст
нельзя молча загрузить: запрос отклоняется прикладной проверкой ссылок.

Результат: `fragments[]`, `findings[]`.

- `FragmentCandidate`: `local_id`, `segment_key`, `quote`, `occurrence` (целое ≥0).
  Цитата — точная непустая подстрока без нормализации регистра/пробелов.
  Вхождения нумеруются с нуля по всем начальным позициям, включая перекрытия.
  Приложение вычисляет положение; цитата не пересекает границу сегмента.
- `FindingCandidate`: `local_id`, `text`, `types[1+]`, `mode`,
  `fragment_ids[1+]`, `considered_keys[1+]`, `context_keys[]`.
  Основания — локальные фрагменты ответа, рассмотренные ключи — сегменты,
  контекстные — документы. Разные прямой и выведенный смыслы разделяются.
- Надёжность фрагмента наследуется программно. Точная цитата из ненадёжного
  транскрипта не становится достоверным свидетельством.

### 7.2 group_findings

Вход: `findings[1+]`, `fragments[]`, `documents[]`, необязательные `previous_groups[]`.
Результат: `groups[]`, `ungrouped_finding_keys[]`.

`GroupCandidate`: `local_id`, `title`, `summary`, `finding_keys[1+]`,
`considered_keys[1+]`, `context_keys[]`, `conflicts[]`.
`ConflictCandidate`: `local_id`, `description`, `positions[2+]`.
В позициях перечисляются переданные находки. Группировка сохраняет противоположные
ожидания, а не выбирает согласованную позицию. Каждая успешно обработанная
находка находится в группе либо явно оставлена негруппированной; одновременная
принадлежность нескольким группам допустима. В общей аналитике находка одна.

### 7.3 generate_requirements

Вход: `findings[1+]`, `fragments[1+]`, `groups[]`, `documents[]`, необязательные
`previous_candidates[]: RevisionView[]`, `change_reason`.
Результат: `requirements[]`.

`RequirementCandidate`: `local_id`, `title`, `text`, `rationale`,
`evidence: EvidenceSelection[1+]`, `considered_keys[1+]`, `context_keys[]`.
Рассмотренный набор находок отделён от выбранных подтверждений; контекстные
ключи — группы и документы. Возможны отношения один-ко-многим в обе стороны.
Отдельное поле критериев приёмки не входит в контракт, как подтвердил пользователь.

Существенно неоднозначная доработка, неразрешимый конфликт либо зависимость
смысла от ненадёжного участка требуют вопроса вместо уверенного кандидата.
Наличие одного формально пригодного фрагмента не доказывает достаточность
всего утверждения. Генератор не назначает номер редакции и не возвращает команду
замены существующего требования. Новое формирование — отдельные кандидаты.

### 7.4 verify_requirement

Вход: `target: RevisionView`, `findings[]`, `fragments[]`, `documents[]`,
`comparisons[]`, `comparison_scope`, `previous_checks[]`.
Необязательные поля (условную необходимость проверяет приложение):

| Поле | Состав и условие |
|---|---|
| `prior_decision` | `ref: HumanDecision`, `revision_ref`, `summary`; обязательно при наличии относящегося прежнего решения |
| `change_context` | `base_revision_ref`, `reason`; при проверке изменения объясняет связь с собственной исходной редакцией |
| `followup` | `previous_result_ref`, `issue_refs[]`; связь целевого повтора |

Все ссылки `previous_groups` и `previous_candidates` замыкаются на явно
переданные находки/фрагменты и выбранные состояния. Отсутствующий контекст
отклоняется по AP-02/AP-03; новые состояния не подставляются автоматически.

`PreviousCheckView`: `ref`, `revision_ref`, `issues[]`.
`PreviousIssueView`: `ref`, `text`, `category`, `severity`, `blocking`, `is_open`,
необязательное `resolution_summary: {ref: IssueResolution, text}`.
Решения и разрешения — факты, сформированные приложением; AI их не переносит.

Результат: `checks[4]`, `issues[]`. Должна быть ровно одна оценка каждого вида
`support`, `contradictions`, `ambiguity`, `duplicates`.

- `CheckAssessment`: `kind`, `conclusion: no_issue_found|issues_found|inconclusive`,
  `rationale`, `considered_keys[]`.
- `IssueCandidate`: `local_id`, `category`, `text`, `reason`, `severity`,
  `blocking`, `blocking_reason`, `related[1+]`, `question_ids[]`.
- Категории: `unsupported_claim`, `contradiction`, `ambiguity`,
  `possible_duplicate`, `insufficient_evidence`. Серьёзность: `low|medium|high`.
- `no_issue_found` относится только к фактически рассмотренному контексту.
  Общего `passed`, `verified=true`, `Approved` или команды закрытия старых
  замечаний в ответе нет. Новые обнаружения имеют собственную идентичность.

## 8. Дубли: состав, область и пакеты

`ComparisonRevision`: `key`, `ref`, `requirement_id`, `roles[1+]`,
`proposal_ref?`, `title`, `text`.

| Роль | Смысл |
|---|---|
| current | Текущая редакция неотклонённого требования |
| pending_change | Текущая кандидатная редакция незавершённого предложения; proposal_ref обязателен |
| new_candidate | Принятый и сохранённый кандидат нового требования текущей обработки |
| history | Дополнительный исторический контекст |

По умолчанию приложение объединяет первые три набора одного проекта;
исторические редакции добавляются при необходимости. Точная цель исключается.
Совпадающие редакции передаются один раз с объединением ролей. Сохранившееся
неотклонённое требование с утраченным источником из сравнения не исключается.
Сходство собственной исходной и новой редакции не создаёт отдельного требования.
`possible_duplicate` должно указывать хотя бы на одно **другое** `requirement_id`.
Редакции чужих незавершённых предложений сравниваются обычным образом.

`comparison_scope = {extent, required_keys, selection_reason?}`:
`extent` — `project_snapshot` либо `selected`; причина обязательна только
для `selected`. `required_keys` перечисляет все предусмотренные сравнения.
Пустой набор допустим, если приложение установило, что он действительно пуст.
Состав, роли, состояния редакций и указатели незавершённых предложений фиксируются
приложением для `request_id`, а не сообщаются моделью как доказанный факт.

| Область | Полнота рассмотрения | Допустимый вывод |
|---|---|---|
| project_snapshot | Полная | Предусмотренный набор на зафиксированный момент рассмотрен |
| selected | Полная | Рассмотрен только выбранный набор |
| Любая | Неполная | Предусмотренная проверка не завершена |

В `duplicates.considered_keys` перечисляются рассмотренные ключи сравнений.
Остальные оценки могут ссылаться на цель, находки, свидетельства и документы.
При ограниченной выборке запрещён вывод об отсутствии дублей во всём проекте.
Полное покрытие может оставаться семантически `inconclusive`.

Для MVP достаточен один логический запрос. При превышении контекста допустимы
фиксированные внутренние пакеты с общей целью и составом снимка; они не вводят
новых операций/ролей и не публикуются как отдельные `VerificationResult`.
Оболочка агрегирует только валидные ответы; технические причины знает приложение.
Один агрегат проходит атомарный приём. При пропусках допустим валидный частичный
агрегат с найденными обнаружениями, явным покрытием и `partially_processed`.
Невалидный агрегат отклоняется целиком; повреждённые ответы не «исправляются».

Найденные замечания не теряются при неполном охвате. `issues_found` не доказывает
полноту; `no_issue_found` допустим лишь после всех предусмотренных сравнений
без неразрешённой смысловой неопределённости. При отсутствии замечаний и наличии
пропущенных сравнений — `inconclusive`. Проверка состава нужна также перед
публикацией: новый кандидат или изменение предложения может сделать вывод
об отсутствии дублей устаревшим, даже если старые тексты не изменились.

## 9. Прикладные проверки вне JSON Schema

JSON Schema проверяет структуру, но не соединяет запрос с ответом и хранилищем.
Необходимые прикладные проверки перечислены отдельно; их наличие в документе
не означает, что будущий backend уже реализован.

| Код | Проверка |
|---|---|
| AP-01 | Полномочия запуска/доступа; все данные одного проекта; регистрация не открывает чужие данные |
| AP-02 | Уникальность ключей/локальных ID, тип и существование каждой ссылки, отсутствие самовольной загрузки контекста |
| AP-03 | Точные состояния входов и выбранного набора оснований; не подставлять новые состояния |
| AP-04 | Границы, длина текста и интервалы; точное вхождение цитаты и соответствие источнику |
| AP-05 | Наследование надёжности, сохранение неопределённости; не повышать надёжность наличием ссылки |
| AP-06 | Выбранные фрагменты действительно относятся к находке; группа/документ не подменяют путь к отзыву |
| AP-07 | Одна coverage-запись на основной ключ; объяснения при отсутствии результата; фактические пропуски определимы |
| AP-08 | Состав групп и конфликтующих позиций; отсутствие потери независимых пригодных результатов |
| AP-09 | Полный предусмотренный состав сравнений, роли предложений, точная цель, разные Requirement.id для возможного дубля |
| AP-10 | Согласованность checks/issues/questions; scope блокировки; существенный вопрос не маскируется как информационный |
| AP-11 | Проект/источники существуют в ожидаемом состоянии; активность попытки; проверка и публикация логически защищены от гонки |
| AP-12 | Старые блокеры/вопросы не исчезают, разрешения не наследуются, новое утверждение — только решение уполномоченного человека |
| AP-13 | После удаления нет восстановления через DTO/журналы/кеш; историческая ссылка содержит только ID источника и факт удаления |
| AP-14 | Условно обязательный prior_decision и связи followup/change_context правдиво подготовлены приложением |

Смысловая поддержка цитатой, достаточность, действительная неоднозначность,
дубли и серьёзность требуют AI/экспертной оценки. AP-05/AP-10 содержат как
программно проверяемые связи, так и ограничения, которые нельзя доказать одной
структурной проверкой. Программный валидатор не объявляет вывод истинным.

## 10. Ошибки, версии результатов и решения человека

Техническая оболочка различает `returned` (получен ответ до приёма) и `failed`.
Коды технических ошибок: `timeout`, `provider_error`, `invalid_response`,
`cancelled`; это метаданные приложения, не поля AI-ответа и не lifecycle Requirement.
Невалидная единица не передаётся дальше. Ручной повтор не стирает другие
успешные независимые результаты. Технический повтор, новая генерация,
проверка актуальности без AI и повторная содержательная проверка различаются.

После приёма выбранные связи превращаются в предметные ссылки. Сохранённая
редакция неизменяема; новая формулировка/набор оснований создаёт новую редакцию.
`VerificationResult` и `HumanDecision` привязаны к точной редакции и рассмотренным
состояниям. Человеческая правка и действующее Approved не перезаписываются AI.
Старый блокер/существенный вопрос проверяется приложением независимо от нового
ответа. Принятие риска не закрывает блокер; неприменимость требует утверждённых
прав, обоснования и истории. Поздний результат не восстанавливает удалённый проект.

## 11. Проверяемость, примеры и команды

[manifest.json](contracts/ai/examples/manifest.json) перечисляет **все** полные
демонстрационные документы, ожидаемый структурный исход и пары запрос–ответ.
Каждый негативный пример имеет ожидаемое нарушенное ключевое слово.
`application-invalid.*` намеренно проходят JSON Schema и отклоняются указанной
офлайн-проверкой связности: это показывает границу структурной валидации.

Из корня репозитория в отдельном Python-окружении:

```text
python -m pip install -r scripts/requirements-ai-contracts.txt
python scripts/validate_ai_contracts.py
```

Проверочный инструмент: Python 3.12 и `jsonschema==4.26.0` (только development
validation). Используются `Draft202012Validator.check_schema` и локальный
`referencing.Registry`; сетевого разрешения $ref нет.
Справка: [валидация](https://python-jsonschema.readthedocs.io/en/stable/validate/),
[локальный реестр](https://python-jsonschema.readthedocs.io/en/stable/referencing/).

Скрипт проверяет метасхемы, все ссылки, перечень файлов, позитивные и негативные
примеры, запрет неизвестного поля во всех объектах позитивных примеров.
Офлайн-правила пар: APP-KEYS, APP-COVERAGE, APP-LINKS, APP-LOCATOR, APP-QUOTE,
APP-EVIDENCE, APP-GROUPING, APP-COMPARISON, APP-DUPLICATE. Это проверки
представленных примеров, **не полный прикладной приём** и не проверка AP-01–AP-14
в реальном приложении. Нулевой exit code относится только к этим проверкам.

Нужны будущие экспертные сценарии: неоднозначные отзывы, противоречия,
выдуманные детали, ненадёжность, существенность вопросов, достаточность после
утраты, собственная редакция и чужое предложение. Модели сравниваются на одинаковых
входах по явным критериям без требования одинаковых формулировок. Численные
пороги, реальные наборы и метрики не установлены.

## 12. Диагностика и границы следующего этапа

Полезны request/attempt-связи, версии схем/шаблона/адаптера, данные модели и настроек
при наличии, длительность, технический исход, пути ошибок, ссылки на принятые
результаты и охват. Сырые запросы/ответы не предлагаются как долговечный журнал
по умолчанию. Условия расширенной диагностики и очистки определяются отдельно
с соблюдением утверждённых границ удаления и условий внешнего провайдера.

Открыты: провайдеры, SDK, библиотека приложения, физические состояния/идентификаторы,
лимиты/сегментация, размеры пакетов, критерий существенности правок, сроки очистки,
численные AI-метрики. Они не меняют утверждённые обязанности и структуры 1.0
без отдельного change control. Следующий этап реализации приложения требует
собственного разрешённого объёма и утверждения отсутствующих технических решений.
