## 1. Наблюдаемое поведение и граница

Member явно запускает `inspect_text` для 1–32 сохранённых текстовых отзывов/
документов одного проекта. Каждая запись — независимая единица задания.
Worker читает ровно указанное текущее состояние и реально вычисляет:

- `character_count = len(text)` в Unicode code points;
- `utf8_byte_count = len(text.encode('utf-8', errors='strict'))`.

Сравнение ожидаемого и текущего state_id проверяет пригодность входа до и после
вычисления. Результат содержит только эти числа и ссылки через unit/attempt.
Текст, название документа, хэш содержимого, DTO или копия материала в очереди,
результате и логах не сохраняются. Пример: текст `ё🙂\r\n` даёт 4 code points
и 8 UTF-8 bytes. Это проверка чтения/кодирования/сохранения результата, а не
содержательный анализ, сегментация, находка или оценка качества текста.

Каждый ответ запуска содержит `execution_kind="technical"`,
`operation="inspect_text"`, `ai_performed=false`. Поле execution_mode проекта
не изменяется; mock-ответ AI не создаётся. Добавление материала не запускает
задания. UI Ф1а/Ф1б не расширяется: технический сценарий доступен через HTTP
и проверяется интеграционно. Семантический AI и UI обработки — последующие этапы.

## 2. Физическая модель: новая m02b после m02a

Общие типы: `uuid` приложения; время `timestamptz` по часам PostgreSQL;
счётчики `bigint`; технические enum — `varchar` + CHECK. Все перечисленные
поля NOT NULL, кроме явно отмеченных `?`. Старые миграции не изменяются.
Каждая проектная таблица имеет project_id FK → projects.id и
UNIQUE(project_id,id), когда id не является самим составным ключом.
Межпроектные ссылки запрещены составными FK, а не только проверками Python.

### processing_runs — явно созданная команда

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id | uuid FK |
| initiated_by | uuid FK users.id; глобальный User не принадлежит проекту |
| command_kind | `start` или `retry` |
| operation | только `inspect_text` |
| execution_kind | только `technical` |
| idempotency_key | uuid, из обязательного заголовка Idempotency-Key |
| request_fingerprint | char(64), SHA-256 канонической команды, не содержимого текста |
| created_at | timestamptz, default clock_timestamp() |

UNIQUE(project_id,initiated_by,command_kind,idempotency_key). Fingerprint строится
из закрытой валидированной команды, не исходных байтов HTTP body. Все UUID
сначала разбираются и приводятся к lowercase-форме с дефисами; это относится
также к Idempotency-Key и UUID пути. JSON: отсортированные ключи, без пробелов,
UTF-8; inputs сортируются по `(kind,id,state_id)` после канонизации. Для retry
включаются нормализованные unit_id пути и expected_attempt_id тела.
Эквивалентное написание UUID и перестановка inputs не меняют fingerprint;
изменение материала, состояния или цели retry меняет каноническую команду.
Дубликаты материала отклоняются до сортировки, а не удаляются канонизацией.
Под одним ключом и областью нельзя зарегистрировать другую команду.
Run не хранит дублирующий агрегат состояний: состояние вычисляется из units.

### processing_units — сохраняемое задание и неизменный ожидаемый вход

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id, run_id | uuid; составной FK → processing_runs(project_id,id) |
| source_id?, source_state_id? | uuid; пара для отзыва |
| document_id?, document_state_id? | uuid; пара для документа |
| state | `queued`, `running`, `completed`, `failed`, `cancelled` |
| retry_of_attempt_id? | uuid; составной FK → stage_attempts(project_id,id) |
| created_at | timestamptz |
| finished_at? | timestamptz, только для конечного состояния |

CHECK XOR: заполнена ровно одна полная пара source или document; вторая пара
целиком NULL. Составной FK `(project_id,source_id,source_state_id)` ссылается
на source_text_states(project_id,source_id,id); аналогично для document_states.
UNIQUE(run_id,source_id) и UNIQUE(run_id,document_id) запрещают повтор материала
в одной команде. UNIQUE(retry_of_attempt_id) ограничивает один retry-преемник.
CHECK конечное состояние ⇔ finished_at IS NOT NULL; finished_at >= created_at.
Вход, run и retry-ссылка после создания unit неизменны соглашением репозитория.
Индексы: `(state,created_at,id) WHERE state='queued'`, `(project_id,run_id,id)`.

### stage_attempts — владение одной попыткой

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id, unit_id | uuid; составной FK → processing_units(project_id,id) |
| request_id | uuid UNIQUE; инженерная корреляция, не AI request |
| state | `running`, `completed`, `failed`, `cancelled` |
| owner_token? | uuid случайный; только во время running, не отдаётся HTTP |
| started_at, deadline_at | timestamptz; deadline_at > started_at |
| lease_expires_at? | timestamptz; во время running, <= deadline_at |
| heartbeat_at | timestamptz; >= started_at |
| finished_at? | timestamptz; для конечных состояний, >= started_at |
| reason_code? | `lease_expired`, `deadline_exceeded`, `execution_error`, `input_changed`, `access_revoked` |

UNIQUE(unit_id): один unit имеет одну попытку; ручной retry создаёт новый run/unit.
CHECK: running ⇒ owner_token/lease заполнены, finished_at/reason_code NULL;
конечное состояние ⇒ owner_token/lease NULL, finished_at заполнено.
completed ⇒ reason_code NULL; failed/cancelled ⇒ reason_code заполнен.
Допустимость пары состояния/причины: failed — lease_expired/deadline_exceeded/
execution_error; cancelled — input_changed/access_revoked. Индекс истёкших
попыток `(lease_expires_at) WHERE state='running'`; отдельный индекс `(unit_id)`
не создаётся: его покрывает UNIQUE(unit_id).
Согласованность unit.state/attempt.state обеспечивается одной общей транзакцией
репозитория и проверяется тестами; не заявляется одним CHECK между таблицами.

### technical_results — однократный сохранённый исход

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id, attempt_id | uuid; составной FK → stage_attempts(project_id,id) |
| character_count | bigint, > 0 |
| utf8_byte_count | bigint, >= character_count |
| created_at | timestamptz |

UNIQUE(attempt_id). Результат существует только у completed-попытки; вставка
результата и оба перехода в completed коммитятся атомарно. Связь с точным
материалом идёт через attempt → unit, не через нетипизированный JSON.
Числа не являются Finding, coverage AI или подтверждением требования.

Новая миграция создаёт четыре таблицы, необходимые FK/UNIQUE/CHECK/индексы;
циклический FK retry_of_attempt_id добавляется после создания attempts.
Существующие строки не переписываются. Downgrade с удалением таблиц не
предоставляется для рабочей БД. Проектные FK предусматривают ON DELETE CASCADE
для будущего согласованного удаления проекта; удаление User не каскадирует их.
Пользовательского удаления материала/проекта И2б не добавляет. Перед реализацией
будущего удаления результаты/refs очереди включаются в отдельный анализ очистки.

## 3. HTTP: только эти три операции

Префикс `p = /api/v1/projects/{project_id}`. Существующие cookie/Origin/CSRF,
ошибки, request_id, no-store и неизвестные поля применяются без ослабления.
GET не запускает работу. Доступ — текущий Member (включая Owner/Approver).

### POST p/runs

Обязателен `Idempotency-Key: <uuid>`. Закрытая форма тела:

```json
{
  "operation": "inspect_text",
  "inputs": [
    {"kind": "source", "id": "<uuid>", "state_id": "<uuid>"},
    {"kind": "document", "id": "<uuid>", "state_id": "<uuid>"}
  ]
}
```

inputs: 1–32; один материал не повторяется, даже с другим state_id. Все refs
сервер проверяет внутри проекта. Нужны текущие доступные состояния.

| Проверка ссылки после проверки проектного доступа | HTTP / code |
|---|---|
| Неизвестный или межпроектный материал | Одинаковая 404 `not_found` |
| Неизвестный или межпроектный state_id при доступном материале | Одинаковая 404 `not_found` |
| State другого материала этого же проекта, включая другой вид материала | 422 `invalid_input` |
| Прежний state нужного материала | 409 `input_changed` |
| Текущий state нужного доступного материала | Допустимый вход |

Сначала материал ищется по kind/id внутри project_id. Затем state ищется только
в таблицах текстовых состояний этого проекта; тип и владелец сверяются до
current_state. Глобальный поиск существования state запрещён: 404 не сообщает,
существует ли он в другом проекте. Ошибка не отражает присланные/чужие значения.
Запуск всех начальных units создаётся одной транзакцией: частичного HTTP-успеха нет.

### GET p/runs/{run_id}

Ответ 200 или одинаковая 404 для недоступного/чужого run. Форма Run:

```json
{
  "id": "<uuid>", "operation": "inspect_text", "execution_kind": "technical",
  "ai_performed": false, "state": "queued", "created_at": "<UTC RFC3339>",
  "units": [
    {
      "id": "<uuid>", "input": {"kind": "source", "id": "<uuid>", "state_id": "<uuid>"},
      "state": "queued", "retry_of_attempt_id": null, "attempt": null
    }
  ]
}
```

Для существующей попытки attempt содержит только id, request_id, state,
started_at, finished_at (null до завершения), reason_code (или null),
result (null либо `{id,character_count,utf8_byte_count,created_at}`). Lease,
owner_token, SQL/исключения и тексты не возвращаются. Units сортируются по id.
Агрегат run: все queued → queued; есть queued/running → running (в том числе
часть уже конечна); все completed → completed; все cancelled → cancelled;
все failed → failed; остальные полностью конечные комбинации → partial.
Для точного различения queued/running клиент читает также units; partial не
выдаётся за полный успех. Один GET использует согласованный read snapshot,
чтобы состояние и units не относились к разным коммитам.

### POST p/units/{unit_id}/retries

`Idempotency-Key: <uuid>`; тело `{ "expected_attempt_id": "<uuid>" }`.
Только failed, текущие права и прежние входы не изменены. Создаёт новый run
с одной queued-unit, тем же входом и retry_of_attempt_id. Старый run/attempt
не переписываются. Retry-попытка появляется при захвате worker, не при HTTP POST.
completed/running/queued/cancelled или неверный expected_attempt_id →
409 retry_not_allowed. Изменённый вход → 409 input_changed: нужен новый start.
Два разных ключа не создают две ветви: UNIQUE retry_of_attempt_id, проигравший
получает 409 retry_already_requested. Повтор той же команды с тем же ключом
возвращает тот же новый run, без новой unit.

Оба POST отвечают 202 той же формой Run; при повторе ключа — актуальное
представление прежнего run. Сначала повторно проверяются доступ и fingerprint,
потом возвращается прежний run. Тот же ключ с другим телом → 409
idempotency_conflict; отсутствие/неверный UUID ключа или неверное тело → 422.
GET требует сессию; POST — дополнительно Origin и текущий CSRF. POST не
повторяется клиентом автоматически. 202 означает сохранение команды, не её успех.

## 4. Транзакционный протокол

Один worker последовательно исполняет задания. Короткие write-транзакции
READ COMMITTED используют порядок `Project FOR UPDATE → unit → attempt`.
Он совместим с текущим управлением правами И1/И2а. Unit выбирается как кандидат
без удержания блокировки, затем под блокировкой проекта состояние проверяется
заново. Проектные блокировки не удерживаются во время вычисления/ожидания.
Масштабирование на несколько worker этим проектом не утверждается. Каждая
транзакция использует новую ORM-сессию; права и состояния не берутся из кэша
предыдущей транзакции. После ожидания блокировок выполняются свежие чтения.

1. **Start/retry:** блокировать Project; проверить права; обработать
   идемпотентность; проверить refs/предусловия; вставить run/units; commit.
   Конкурентный повтор после ожидания читает уже сохранённую команду.
2. **Claim:** выбрать старейшую queued по (created_at,id); блокировать Project,
   unit; снова проверить queued, доступ инициатора, доступность и current_state.
   Вставить running attempt с новым token; unit → running; commit. При
   отозванном доступе/изменённом входе сразу создать cancelled attempt и
   cancelled unit с причиной; никаких результатов.
3. **Compute:** только после доказанного claim COMMIT и проверки действующего
   владения получить текст точного ожидаемого state в короткой read-транзакции,
   закрыть её, вычислить числа в памяти. Одно вычисление на attempt; неизвестный
   COMMIT не является основанием выполнить его заново. Текст не попадает в
   очередь/логи; после утраты владения локальное выполнение прекращается.
4. **Heartbeat:** отдельное соединение/короткая транзакция в том же порядке;
   условно продлить lease при matching token, running, неистёкших lease/deadline.
   Нельзя оживить уже истёкшее владение. Срок не превышает абсолютный deadline.
5. **Complete:** снова блокировать Project/unit/attempt; проверить token,
   сроки по clock_timestamp(), права инициатора, текущий вход и вид/доступность
   материала. Вставить один technical_result; оба состояния → completed;
   отозвать token/lease; проставить finished_at; commit одной транзакцией.
   Последний условный переход running → completed ещё раз проверяет token и
   сроки по clock_timestamp(); если он не выполнен, вся транзакция с result
   откатывается. Ранняя проверка не разрешает переход после истечения срока.
6. **Ошибка/отмена:** в том же протоколе записать только безопасный reason_code,
   оба конечных состояния, finished_at; отозвать владение. Содержимое exception
   и текст не сохраняются. Зависимых этапов/автоматического продолжения здесь нет.

Приоритет проверки в completion: существование проекта/владение/срок →
текущие права → текущий вход → результат. Истёкший владелец не меняет попытку,
включая её причину; recovery завершает её как failed. Изменённый вход или
утраченное членство отменяет результат. Чужой выход не публикуется даже при
совпадающих числах. Успех одной unit не откатывается при ошибке другой.

Допустимые переходы (конечные записи не переписываются):

| Объект / исходное состояние | Следующее состояние / условие |
|---|---|
| unit: queued; attempt отсутствует | running/running при успешном claim либо cancelled/cancelled при непригодном входе/правах |
| unit/attempt: running/running | completed/completed с одним result; failed/failed; cancelled/cancelled |
| unit/attempt: любое конечное | Переходов нет; reconciliation только читает, recovery не меняет конечный исход |
| Ручной retry failed | Новый run и queued-unit без attempt; затем обычный claim. Старые строки не меняются |

У queued нет attempt/result и finished_at. В остальных состояниях unit имеет
ровно один согласованный attempt; result существует тогда и только тогда,
когда оба completed. Межтабличные инварианты обеспечивает общий репозиторий
в одной транзакции; DDL не объявляется их полной заменой. Подтверждённый rollback
отменяет все её записи; ошибка связи не доказывает rollback (§5.3).
cancelled не переводится в failed ради разрешения retry.

## 5. Восстановление и остановка

### 5.1. Ограничения ожидания и их обоснование (C1)

Это начальные инженерные параметры для локального PostgreSQL 17 и короткого
inspect_text, не SLA или новые продуктовые лимиты. Они относятся к соединениям
worker/его healthcheck, не меняют настройки backend или мигратора.

| Параметр | Значение / назначение |
|---|---|
| poll / heartbeat / lease / deadline | 1 / 5 / 20 / 60 s, как в ревизии 1 |
| connect_timeout / ожидание свободного соединения пула | 3 / 3 s; ограничены подключение и выдача соединения |
| lock_timeout | 2 s; очередь не ждёт проектную блокировку бессрочно |
| statement_timeout | 5 s; ограничивает каждый SQL-запрос |
| transaction_timeout | 8 s; ограничивает всю транзакцию PostgreSQL 17 |
| Бюджет I/O | 10 s по monotonic: получение соединения и одна read/write-транзакция целиком; вычисление сюда не входит |
| Compute inspect_text | До 45 s, дополнительно ограничено остатком deadline за вычетом 10 s резерва на completion; срок фиксируется при входе в compute |
| Абсолютный deadline попытки | 60 s от started_at по часам БД; фиксируется при claim и никогда не продлевается heartbeat/reconnect |
| Startup | 15 s на локальную инициализацию до первого обращения к БД; ожидание доступности БД в этот срок не входит |
| Recovery | Не более 30 s на ограниченный проход, включая текущую транзакцию; незавершённый остаток проверяется в следующем проходе |
| Ожидание reconnect | 1, 2, 4, 8, 15 s, далее 15 s; бюджет одной фазы ожидания 20 s |
| Reconciliation | 30 s от первого неизвестного COMMIT; не продлевается при повторных ошибках, владение может закончиться раньше |
| SIGTERM / stop_grace_period | 30 s; ограниченное завершение текущего действия без новых claims |
| Healthcheck | interval=5 s, timeout=8 s, retries=1, start_period=15 s |
| Публикация локального состояния | Ожидание lock не более 1 s; ошибка собственного канала наблюдения — ненулевой выход worker |

Соотношения: `0 < lock_timeout < statement_timeout < transaction_timeout <
io_budget`, `heartbeat + io_budget < lease < deadline`,
`compute_budget + completion_reserve < deadline`; completion_reserve=io_budget.
Все интервалы положительны; reconnect wait < его бюджета, probe budget=6 s <
healthcheck timeout. Конфигурация с нарушением соотношений отклоняется до claim.

Две секунды оставляют коротким проектным writers время завершиться; 5/8 s
ограничивают запрос и транзакцию из нескольких действий. 10 s дают запас к
локальному SQL. Это вложенные пределы, не разрешение сложить все ожидания:
учитывается остаток бюджета I/O и внешнего срока recovery/reconciliation/stop.
45 s отделяют вычисление от I/O и оставляют резерв completion в 60 s попытки.
При входе в compute его локальный предел равен меньшему из now+45 s и
локального предела попытки минус 10 s; если времени не осталось, вычисление
не начинается. Если compute не завершена и переход из неё не опубликован до
compute-предела, её результат не принимается: действующий владелец завершает
попытку execution_error, при утрате владения её завершит recovery. Своевременно
завершённая compute не делает результат просроченным только из-за более позднего
completion/reconciliation: остаются обязательны сроки попытки/lease и §5.3.
Watchdog остаётся последним уровнем защиты.

Для локального watchdog 60 s фиксируются непосредственно перед транзакцией
claim по monotonic: это консервативная граница, не более поздняя, чем deadline
созданной попытки при обычном ходе часов БД. Она не пересчитывается после
heartbeat/reconnect. Публикация всегда проверяет также реальные сроки БД.
Heartbeat имеет отдельное соединение; интервал 5 s оставляет запас до lease=20 s.
Конкуренция или медленная БД могут привести к потере lease; поздний успех запрещён.

Пример: 30-секундное вычисление при достаточном остатке deadline и действующем
heartbeat допустимо; истечение 10 s I/O к нему не применяется. Для будущего
AI-обработчика длительность compute и deadline задаются отдельно от коротких
транзакций и периода heartbeat. Значения 45/60 s относятся только к inspect_text;
AI-вызовы и их параметры здесь не утверждаются и не реализуются.

Параметры SQL устанавливаются для каждого соединения worker до рабочих запросов,
включая новые соединения после reconnect. Подтверждённо прерванная транзакция
откатывается; повреждённое соединение исключается из пула. Timeout/разрыв около
COMMIT не считается доказательством rollback: применяется §5.3. Серверные timeout
не ограничивают ожидание потерянного сетевого ответа клиентом; зависший I/O
завершает механизм §5.4. Повтор SQL не означает повтор всего вычисления.

Основания: [PostgreSQL 17: SQL timeout](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-STATEMENT-TIMEOUT),
[libpq: connect_timeout](https://www.postgresql.org/docs/17/libpq-connect.html#LIBPQ-CONNECT-CONNECT-TIMEOUT).
connect_timeout действует на адрес подключения, не является общим пределом DNS/
всего цикла; локальная конфигурация использует один endpoint БД. Часы БД проверяют
lease/deadline; monotonic ограничивает локальные ожидания и не заменяет fencing.
Это исходные настройки для реализации/проверки, не результаты измерения.

### 5.2. Запуск, reconnect и recovery

Startup=15 s охватывает конфигурацию, проверку локальных возможностей watchdog
и публикацию начального состояния (§5.4); до этого обращений к БД и claims нет.
После локального startup worker проверяет схему по правилам check_schema DEC-011,
без миграций/DDL, с ограничениями §5.1. Неверная/старая/более новая схема —
невосстановимое состояние: безопасная диагностика, ненулевой выход, без claims.
После исправления образа/схемы проверка выполняется заново. Обновление
несовместимого образа предполагает остановку старого worker, а не online-миграцию
под ним. Недоступная БД при старте — временный сбой: процесс остаётся неготовым
и подключается повторно с указанным backoff. Схема проверяется также после
reconnect и перед claim.

При старте и в цикле recovery выбирает running с lease/deadline <= времени БД.
Проход имеет непродлеваемый предел 30 s; каждая транзакция ограничена также
остатком прохода и 10 s I/O. По исчерпании времени новый кандидат не начинается,
текущая транзакция завершается/откатывается, остаток переносится в следующий
проход без объявления его обработанным. Между транзакциями есть реальный
прогресс цикла; это не одна транзакция или бессрочная глобальная блокировка.
Для каждого кандидата под Project/unit/attempt lock заново проверяется истечение;
оба состояния → failed, reason=deadline_exceeded (приоритет) либо lease_expired,
token/lease NULL, finished_at. Recovery идемпотентен. При timeout блокировки
транзакция откатывается, кандидат остаётся для следующего прохода; результат
не считается восстановленным. Отдельного recovery-сервиса нет.
Начальная готовность требует одного завершённого ограниченного прохода,
в том числе пустого; она не означает, что все исторические ошибки уже устранены.

Неистёкшая старая попытка ожидает срока: restart не доказывает потерю. queued
сохраняются, failed/cancelled не исполняются автоматически. Recovery не создаёт
новые run/unit/attempt и не возвращает running в queued. Новый процесс не
восстанавливает owner_token из tmp/логов; старые running только ожидают срока
и проходят recovery. Технический retry failed остаётся ручным HTTP POST.

При разрыве БД/неподтверждённом heartbeat новые claims прекращаются, локальное
исполнение приостанавливается. После восстановления: проверка схемы →
reconciliation неизвестного claim/completion COMMIT, если он есть → recovery →
повторная проверка прежнего владения перед продолжением. Доказанная утрата
token/состояния/срока прекращает локальную работу и heartbeat; результат
отбрасывается. Неподтверждённое продление heartbeat не считается состоявшимся:
после reconnect читаются сохранённые token/сроки, а не локальный предполагаемый
lease. Просроченную попытку завершает только recovery. При временной
недоступности БД без зависания процесс продолжает backoff, не создаёт restart-loop
и не изображает готовность. Фатальная ошибка или исчерпанный reconciliation
приводит к ненулевому выходу, а не к произвольной перезаписи попытки.

### 5.3. Reconciliation неизвестного COMMIT (C2)

UUID attempt/request/result и token назначаются до соответствующего COMMIT и
сохраняются в памяти процесса вместе с unit/project и фактом уже выполненного
вычисления. Полный текст после вычисления не удерживается ради reconciliation.
Потерянное подтверждение не означает rollback. На время неопределённости новые
claims, вычисление и публикация запрещены; heartbeat не продлевает неразрешённую
локальную операцию. Повтор всей unit вместо reconciliation запрещён.

1. Исключить прежнее клиентское соединение из использования. Его закрытие само
   по себе не доказывает исход на сервере. Начать фиксированный бюджет 30 s;
   не переносить его при reconnect или промежуточном SELECT.
2. Восстановить соединение и проверить схему. В новой READ COMMITTED транзакции
   взять Project FOR UPDATE → unit FOR UPDATE → существующий attempt FOR UPDATE.
   Прежний claim/completion держит ту же Project-блокировку до конца транзакции.
   Нельзя обойти её NOWAIT/SKIP LOCKED и объявить отсутствующий attempt rollback.
3. Если предыдущая транзакция ещё не закончена, ждать только в пределах timeout.
   При timeout откатить новую транзакцию и повторить reconciliation с backoff,
   не вычисляя/публикуя. После получения Project-блокировки отдельными свежими
   SELECT перечитать unit, attempt и result; решение не основывается на снимке
   до ожидания. Проверить принадлежность известным UUID и согласованность §4.
4. Применить таблицу ниже. Любое продолжение running требует прежнего token,
   неистёкших lease/deadline по clock_timestamp() и обычных проверок §4.
   Reconciliation не возрождает истёкшее владение и не создаёт новое.
5. Если установить исход нельзя за 30 s, либо выявлена несогласованность записей,
   прекратить локальную обработку, выдать безопасный технический код и завершить
   процесс ненулевым кодом. Не объявлять unit failed вслепую. После restart
   применяется §5.2: сохранённый running истечёт, queued остаётся queued.

| Состояние после сериализованного перечитывания | После неизвестного claim COMMIT | После неизвестного completion COMMIT |
|---|---|---|
| Свой running, result отсутствует, владение действительно | Claim доказан; после закрытия reconciliation-транзакции впервые читать/вычислять | Предыдущая публикация не сохранилась; допустима повторная транзакция completion с теми же result UUID и числами из памяти, без повторного вычисления |
| Свой completed, ровно один соответствующий result, unit completed | Признать сохранённый исход, ничего не вычислять/вставлять | Признать успех прежнего COMMIT, ничего не вставлять |
| Свой failed/cancelled | Отбросить локальную работу; конечный исход не менять | То же; никакого автоматического retry |
| Свой running, но token не совпадает либо lease/deadline истёк | Не продолжать; отозванный/просроченный владелец ничего не меняет | То же; числа отбрасываются, истечение оформляет recovery |
| Attempt отсутствует; unit queued, не имеет другой попытки/result | Только после получения блокировок это доказанный несохранённый claim. Закрыть локальную операцию без вычисления; unit доступна обычному следующему claim | Несогласованность: до вычисления claim уже был доказан. Завершить процесс, не создавать попытку и не вычислять заново |
| Другой attempt у unit, противоречащие состояния, completed без result или result у не-completed | Не присваивать чужой успех; безопасная ошибка целостности и выход | То же |
| Нет проекта или unit | Отбросить локальную работу; не восстанавливать строки | То же; не объявлять отсутствующий результат опубликованным |
| БД недоступна / блокировки не получены / результат не установлен | Оставаться в reconciliation до его предела, затем выход без записи исхода | То же |

Если после неизвестного completion чисел в памяти уже нет, пересчитывать их
нельзя: процесс завершается ненулевым кодом без публикации, running завершит recovery.
Если повторный completion COMMIT снова неопределён, используется та же процедура
с исходным бюджетом, UUID и числами. Приоритет expiry/прав/входа остаётся §4;
отзыв прав или смена входа приводит к отмене, не к принятию сохранённых чисел.
Heartbeat возобновляется только после доказанного действующего владения.
UNIQUE(attempt_id), блокировки и конечные переходы защищают однократную публикацию.
Это не обещание однократности будущего внешнего AI-вызова и не протокол 2PC.

### 5.4. Healthcheck и действие при зависании (C1)

Для будущего контейнера worker предусматриваются `init: true` и exec-запуск
Python без shell-обёртки: встроенный init Docker — PID 1, единственный исполнитель
очереди — его дочерний Python-процесс. Init только передаёт сигналы/собирает
процессы; он не читает БД и не выполняет recovery. Нового сервиса нет.
Внешний probe выбран для наблюдения независимо от Python/GIL и heartbeat.
Встроенный watchdog-поток проще, но не переживает остановку всего процесса;
отдельный контейнер/собственный supervisor для И2б не вводятся.

**Канал состояния.** До БД worker публикует в tmp небольшую запись: PID/время
старта из /proc, идентичность родителя-init, монотонно растущий sequence, фазу,
начало/предел фазы, непродлеваемые внешние пределы и признак готовности. Для
running отдельно отмечаются I/O heartbeat и консервативный локальный предел
подтверждённого lease. Продление этого предела допустимо только после доказанного
heartbeat COMMIT; его проекция строится от monotonic до запроса, а не после
получения ответа, и ограничена общим пределом попытки. Нет текста, токенов или DTO.

Основной цикл и heartbeat сериализуют публикацию общим mutex внутри worker.
Для согласования с probe writer берёт exclusive flock на отдельном стабильном
lock-файле, заменяет запись атомарно и освобождает lock. Lock-файл не заменяется
вместе с записью. Ожидание
writer суммарно для mutex/flock ограничено 1 s; под lock нет SQL, вычислений,
sleep или ожидания соединения.
Действие новой фазы не начинается до публикации. Завершение фазы считается
зафиксированным после публикации перехода; просроченный срок нельзя обнулить
записью новой рабочей фазы. После истечения допустим только отказ от результата,
ограниченная запись ошибки при действующем владении либо stopping; новое
вычисление/публикация успеха запрещены. Чередование фаз/heartbeat не продлевает
deadline попытки, compute, reconciliation, recovery-прохода или stopping.

Фазы имеют пределы §5.1: startup=15 s, I/O=10 s, compute до 45 s с резервом,
idle poll=10 s, reconnect wait=20 s, recovery-проход=30 s, stopping=30 s.
На вложенном I/O действует меньший из его предела и внешнего срока. Длительная
compute не требует периодического фиктивного обновления прогресса: до своего
зафиксированного предела она допустима. Heartbeat не обновляет основной прогресс;
его зависший I/O или истёкший подтверждённый локальный lease не скрываются живым
основным циклом. Неизвестное продление не становится новым сроком.

Применимость пределов зависит от режима, а не только от наличия старого attempt:

| Режим | Какой истёкший срок может разрешить сигнал |
|---|---|
| Startup / idle | Только опубликованный срок startup / idle |
| Рабочие claim/read/compute/complete | Срок текущей фазы, попытки; при действующем running также подтверждённый локальный lease / незавершённый I/O heartbeat |
| Reconnect / reconciliation / recovery | Срок текущей контрольной фазы/прохода и вложенного I/O; не прежний lease или deadline приостановленной попытки |
| Stopping | Опубликованный stopping-предел по §5.5; старый snapshot рабочей фазы не используется |

Истечение lease/deadline во время переподключения запрещает рабочее продолжение,
но не делает работающий backoff зависанием. Reconciliation может дочитать уже
completed-исход после истечения прежнего lease/deadline, не вычисляя и не публикуя
заново; это не продление владения. Старый срок восстанавливаемого attempt также
не является сроком текущего recovery-прохода. Незавершённый фактический I/O
heartbeat остаётся ограниченным I/O; простой пропуск heartbeat во время
приостановленной работы не является отдельной причиной убивать reconnect.

**Разрешение на сигнал.** Probe берёт тот же exclusive lock неблокирующим
flock, заново читает целую запись и проверяет её sequence, фазу и пределы.
Данные, прочитанные до lock или в прошлом probe, не разрешают сигнал. Пока lock
удерживается, writer не может опубликовать переход. В этой же критической секции:

1. Проверить целостность записи, существование процесса, PID !=1, время старта,
   ожидаемый entrypoint и непосредственного родителя-init в этом контейнере.
   Открыть pidfd и повторно проверить идентичность; сигнал отправляется через
   pidfd_send_signal, не по повторно использованному числовому PID. Новый процесс
   после restart не наследует идентичность предыдущего.
2. Снять актуальное monotonic-время. SIGKILL разрешён только при доказанном
   истечении применимого фиксированного предела. Startup до своего предела
   защищён независимо от Docker start_period; stopping применяет §5.5.
3. До освобождения lock отправить SIGKILL только установленному процессу через
   pidfd. Это аварийное завершение уже просроченного действия, не успешный stop.
   Исчезнувшая цель не заменяется другим PID. Закрыть дескрипторы/освободить lock.

Lock не удерживается во время проверки БД. Поддержка flock/pidfd и права на
сигнал проверяются локально до claim; целевой путь требует Linux с pidfd_open
(ядро >=5.3) и Python 3.12. Это условие контейнерного watchdog, не выбор будущей
серверной платформы. Неподдерживаемая среда даёт явный отказ запуска заданий;
небезопасного fallback на kill по одному PID нет.

**Без разрешения на сигнал.** Отсутствующая/повреждённая запись, чужая идентичность,
недоступный lock или ошибка проверки процесса дают unhealthy и безопасную причину,
без SIGKILL и без поиска «похожего» Python-процесса. start_period не отменяет
это правило ни до, ни после 15 s. Worker может восстановить свою запись из
согласованного состояния в памяти; если сам не может вести канал наблюдения,
он прекращает claims и завершается ненулевым кодом. Если зависание произошло
до первой записи либо writer завис, удерживая lock, достоверного разрешения
на сигнал нет: нужен операторский restart. Это явное ограничение, а не обещание
автовосстановления любого сбоя канала наблюдения. Такое упрощение исключает
угадывание PID и отдельную систему наблюдения за наблюдателем.

**Проверка готовности.** После освобождения lock probe проверяет БД/точную схему
в отдельном соединении с общим бюджетом 6 s (connect <=3 s, каждый SQL <=1 s).
DDL отсутствует; Docker timeout=8 s ограничивает сам probe. Неуспех/timeout
этой проверки даёт unhealthy, но никогда не разрешает сигнал. Для healthy
нужны допустимая текущая фаза, начальная проверка схемы/ограниченный recovery
и успешный probe БД. Reconnect, reconciliation и stopping не являются готовностью
к новым claims. Idle без работы и compute в разрешённом бюджете не являются
зависанием; повторный snapshot под lock не должен показать истёкшую фазу.

При недоступной БД и работающем backoff процесс остаётся живым. При зависшем
клиентском I/O может истечь именно его локальный бюджет: тогда сигнал разрешён
за нарушение этого срока, а не за недоступность БД. Неизвестный COMMIT после
аварийного выхода разрешается по §5.2–5.3, не повтором failed-задания.

Временной предел определяет разрешённую длительность, а не безошибочно отличает
зависание от замедления. Пауза планировщика может привести к превышению срока;
жёсткая real-time гарантия и нулевое число таких отказов не заявляются. При сбое
канала наблюдения безопаснее unhealthy и ручной restart, чем сигнал без доказательств.
При native запуске без контейнерного probe/restart автоматическое восстановление
зависшего процесса не заявляется. Реальная цепочка рестарта проверяется по §5.6/7.

Основания: [Python flock](https://docs.python.org/3.12/library/fcntl.html#fcntl.flock),
[pidfd_open](https://docs.python.org/3.12/library/os.html#os.pidfd_open),
[pidfd_send_signal](https://docs.python.org/3.12/library/signal.html#signal.pidfd_send_signal),
[Linux PID namespace](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html).

### 5.5. Остановка

SIGTERM через init немедленно запрещает новые claims и переводит worker в stopping
с непродлеваемым пределом 30 s. Текущее действие может завершиться лишь с
действующим владением и обычными проверками, без нового вычисления/retry.
Heartbeat закрывается вместе с локальной работой. При выходе освобождаются
соединения; невосстановимое состояние даёт ненулевой код, штатный stop — нулевой.
Неизвестный COMMIT не объявляется отказом из-за SIGTERM: reconciliation ограничен
также остатком grace. Stopping публикуется под тем же локальным lock. После
перехода probe не использует сохранённый snapshot прежней фазы и не применяет
10 s к освобождению ресурсов. Сроки попытки/lease и запрет результата просроченной
compute продолжают действовать; после отказа от результата cleanup ограничен stopping=30 s.
Это верхняя граница завершения, не обязательное ожидание всех 30 s и не отмена
нарушения срока до SIGTERM. Зависший процесс, не опубликовавший stopping, не
получает новый срок из предположения probe; Docker stop сам ограничивает grace.
По истечении опубликованного stopping-предела probe вправе завершить установленный
процесс по §5.4; Docker также может принудительно закончить stop после grace.
При ручном Docker stop автоматический restart подавляется правилами Docker.
Если attempt остался running, lease истечёт и recovery запишет ошибку.
Тестовые задержки/сбои моделируются инструментарием, не production-операцией.

### 5.6. Условия рестарта контейнера и границы подтверждения

Планируемая политика — `restart: on-failure` без лимита аварийных рестартов.
Цепочка «probe → SIGKILL worker → ненулевой выход init → restart контейнера»
действует только если Python — непосредственный ребёнок init, нет shell-обёртки
или переназначения ошибочного exit code в 0, probe имеет нужные права, политика
активна, а Docker Engine работает. Для Tini SIGKILL ребёнка даёт 137 без remap;
`init: true` сам по себе не закрепляет конкретную реализацию init на всех платформах.
Фактическое поведение init и всей цепочки необходимо проверить на целевой среде.

Docker документирует условия успешного первоначального старта (в частности,
интервал 10 s) для применения restart policy. Ранний отказ до полноценного
запуска не объявляется гарантированно автоматически восстанавливаемым: отдельно
проверяются аварии до/после 10 s и startup=15 s в поддерживаемых версиях Engine.
Не вводится искусственное ожидание перед claim ради обхода этих условий.
`start_period` только влияет на учёт неуспеха probes: они выполняются в этот
период и способны отправить сигнал; правила §5.4 обязательны всегда.

Ручной Docker stop подавляет автоматический restart. `on-failure` не обещает
автозапуск после перезапуска Docker Engine; оператор запускает стек по действующим
инструкциям и проверяет готовность. Политика не меняется скрыто на always/
unless-stopped и не дополняется внешним управляющим сервисом. Фатальная ошибка
схемы/конфигурации требует исправления причины, рестарт не обходит проверок.
Сам по себе unhealthy или ненулевой exit code probe не завершает worker.

Эта цепочка пока обоснована документально, не подтверждена интеграционным запуском.
При реализации фиксируются Engine/Compose/ядро/init/образы и проверяются ненулевой
исход контейнера, RestartCount, StartedAt и новый экземпляр процесса. Restart
обычно сохраняет ID контейнера; новый ID не является обязательным критерием.
Новая очередь не признаётся принятой без реальных Docker-тестов. Принятие самой
спецификации не требует реализации до разрешения пользователя. Даже после
успешного теста это условная гарантия для проверенной среды, не SLA при отказе хоста.

Основания: [Compose init/restart](https://docs.docker.com/reference/compose-file/services/#init),
[Tini exit codes](https://github.com/krallin/tini#exit-codes),
[Docker restart](https://docs.docker.com/engine/containers/start-containers-automatically/),
[Docker HEALTHCHECK](https://docs.docker.com/reference/dockerfile/#healthcheck).
Init, политика и команда probe только специфицированы; Compose пока не изменён.

После каждого fault/restart проверяются queued/running/failed/cancelled,
отсутствие автоматического бизнес-retry и второй публикации, сохранность прежних
успешных units и безопасные HTTP/логи. Тест рестарта воспроизводит сигнал из
probe, не подменяется docker stop или одним исключением в Python. Сохраняются
версии Engine/Compose/ядра/init, image IDs, Docker events и снимки состояния БД;
числовой PID внутри контейнера может повториться, проверяется новая идентичность.
Бюджеты ожидания тестов учитывают завершение предыдущего probe и Docker backoff:
interval=5 s не означает жёсткий запуск каждые 5 s и не задаёт SLA рестарта.

## 8. Объём запрашиваемого утверждения

На согласование представляется только спецификация: четыре будущие таблицы
m02b, inspect_text, три описанных HTTP-контракта, транзакции/recovery и worker
без AI, включая параметры/механизм восстановления и матрицу проверок ревизии 3.
Утверждение документа не разрешает автоматически создание миграции, реализацию
очереди/worker/API, изменение Compose/CI, запуск миграций или изменение рабочей БД.
Для этого требуется отдельное явное разрешение на реализацию и её объём.

Весь FIRST_TEXT_SLICE, дальнейшие AI-операции/контракты, UI обработки,
редактирование/удаление материалов, платные интеграции и merge в main не входят
в это согласование. Новых продуктовых функций или recovery-сервиса нет.
Независимое ревью ревизии 1 и дополнительная проверка watchdog ревизии 2
выполнены; пользователь принял направление исправлений. Ревизия 3 представлена
для окончательного утверждения. Условия и ограничения автоматического восстановления
описаны явно; runtime-гарантии ещё не проверены, их приёмка требует §7.2.
DECISIONS.md и другие утверждённые документы сейчас не изменяются; после
отдельного согласия в журнале фиксируются точная ревизия и границы утверждения.
