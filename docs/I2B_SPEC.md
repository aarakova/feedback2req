# И2б: PostgreSQL-очередь и технический worker

**PROPOSED / на согласование. Ревизия 1, 2026-10-23.**
DEC-011 утверждает направление и инфраструктуру, но не эту схему, HTTP или
реализацию. Код очереди и новая миграция до отдельного подтверждения не создаются.
Основания: [DEC-003–DEC-011](DECISIONS.md), [модель](DATA_MODEL.md),
[проект среза, ревизия 1](FIRST_TEXT_SLICE.md), [API И1/И2а](API.md).

## 1. Наблюдаемое поведение и граница

Member явно запускает `inspect_text` для 1–32 сохранённых текстовых отзывов/
документов одного проекта. Каждая запись — независимая единица задания.
Worker читает ровно указанное текущее состояние и реально вычисляет:

- `character_count = len(text)` в Unicode code points;
- `utf8_byte_count = len(text.encode('utf-8', errors='strict'))`.

Сравнение ожидаемого и текущего state_id проверяет пригодность входа до и после
вычисления. Результат содержит только эти числа и ссылки через unit/attempt.
Текст, название документа, хэш содержимого, DTO или копия материала в очереди,
результате и логах не сохраняются. Пример: текст `ё🙂\r\n` даёт 4 code points
и 8 UTF-8 bytes. Это проверка чтения/кодирования/сохранения результата, а не
содержательный анализ, сегментация, находка или оценка качества текста.

Каждый ответ запуска содержит `execution_kind="technical"`,
`operation="inspect_text"`, `ai_performed=false`. Поле execution_mode проекта
не изменяется; mock-ответ AI не создаётся. Добавление материала не запускает
задания. UI Ф1а/Ф1б не расширяется: технический сценарий доступен через HTTP
и проверяется интеграционно. Семантический AI и UI обработки — последующие этапы.

## 2. Физическая модель: новая m02b после m02a

Общие типы: `uuid` приложения; время `timestamptz` по часам PostgreSQL;
счётчики `bigint`; технические enum — `varchar` + CHECK. Все перечисленные
поля NOT NULL, кроме явно отмеченных `?`. Старые миграции не изменяются.
Каждая проектная таблица имеет project_id FK → projects.id и
UNIQUE(project_id,id), когда id не является самим составным ключом.
Межпроектные ссылки запрещены составными FK, а не только проверками Python.

### processing_runs — явно созданная команда

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id | uuid FK |
| initiated_by | uuid FK users.id; глобальный User не принадлежит проекту |
| command_kind | `start` или `retry` |
| operation | только `inspect_text` |
| execution_kind | только `technical` |
| idempotency_key | uuid, из обязательного заголовка Idempotency-Key |
| request_fingerprint | char(64), SHA-256 канонической команды, не содержимого текста |
| created_at | timestamptz, default clock_timestamp() |

UNIQUE(project_id,initiated_by,command_kind,idempotency_key). Fingerprint строится
из JSON команды: отсортированные ключи, без пробелов, UTF-8; inputs сортируются
по `(kind,id,state_id)`. Для retry включаются unit_id и expected_attempt_id.
Под одним ключом и областью нельзя зарегистрировать другую команду.
Run не хранит дублирующий агрегат состояний: состояние вычисляется из units.

### processing_units — сохраняемое задание и неизменный ожидаемый вход

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id, run_id | uuid; составной FK → processing_runs(project_id,id) |
| source_id?, source_state_id? | uuid; пара для отзыва |
| document_id?, document_state_id? | uuid; пара для документа |
| state | `queued`, `running`, `completed`, `failed`, `cancelled` |
| retry_of_attempt_id? | uuid; составной FK → stage_attempts(project_id,id) |
| created_at | timestamptz |
| finished_at? | timestamptz, только для конечного состояния |

CHECK XOR: заполнена ровно одна полная пара source или document; вторая пара
целиком NULL. Составной FK `(project_id,source_id,source_state_id)` ссылается
на source_text_states(project_id,source_id,id); аналогично для document_states.
UNIQUE(run_id,source_id) и UNIQUE(run_id,document_id) запрещают повтор материала
в одной команде. UNIQUE(retry_of_attempt_id) ограничивает один retry-преемник.
CHECK конечное состояние ⇔ finished_at IS NOT NULL; finished_at >= created_at.
Вход, run и retry-ссылка после создания unit неизменны соглашением репозитория.
Индексы: `(state,created_at,id) WHERE state='queued'`, `(project_id,run_id,id)`.

### stage_attempts — владение одной попыткой

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id, unit_id | uuid; составной FK → processing_units(project_id,id) |
| request_id | uuid UNIQUE; инженерная корреляция, не AI request |
| state | `running`, `completed`, `failed`, `cancelled` |
| owner_token? | uuid случайный; только во время running, не отдаётся HTTP |
| started_at, deadline_at | timestamptz; deadline_at > started_at |
| lease_expires_at? | timestamptz; во время running, <= deadline_at |
| heartbeat_at | timestamptz; >= started_at |
| finished_at? | timestamptz; для конечных состояний, >= started_at |
| reason_code? | `lease_expired`, `deadline_exceeded`, `execution_error`, `input_changed`, `access_revoked` |

UNIQUE(unit_id): один unit имеет одну попытку; ручной retry создаёт новый run/unit.
CHECK: running ⇒ owner_token/lease заполнены, finished_at/reason_code NULL;
конечное состояние ⇒ owner_token/lease NULL, finished_at заполнено.
completed ⇒ reason_code NULL; failed/cancelled ⇒ reason_code заполнен.
Допустимость пары состояния/причины: failed — lease_expired/deadline_exceeded/
execution_error; cancelled — input_changed/access_revoked. Индекс истёкших
попыток `(lease_expires_at) WHERE state='running'` и индекс `(unit_id)`.
Согласованность unit.state/attempt.state обеспечивается одной общей транзакцией
репозитория и проверяется тестами; не заявляется одним CHECK между таблицами.

### technical_results — однократный сохранённый исход

| Поле | Тип / правило |
|---|---|
| id | uuid PK |
| project_id, attempt_id | uuid; составной FK → stage_attempts(project_id,id) |
| character_count | bigint, > 0 |
| utf8_byte_count | bigint, >= character_count |
| created_at | timestamptz |

UNIQUE(attempt_id). Результат существует только у completed-попытки; вставка
результата и оба перехода в completed коммитятся атомарно. Связь с точным
материалом идёт через attempt → unit, не через нетипизированный JSON.
Числа не являются Finding, coverage AI или подтверждением требования.

Новая миграция создаёт четыре таблицы, необходимые FK/UNIQUE/CHECK/индексы;
циклический FK retry_of_attempt_id добавляется после создания attempts.
Существующие строки не переписываются. Downgrade с удалением таблиц не
предоставляется для рабочей БД. Проектные FK предусматривают ON DELETE CASCADE
для будущего согласованного удаления проекта; удаление User не каскадирует их.
Пользовательского удаления материала/проекта И2б не добавляет. Перед реализацией
будущего удаления результаты/refs очереди включаются в отдельный анализ очистки.

## 3. HTTP: только эти три операции

Префикс `p = /api/v1/projects/{project_id}`. Существующие cookie/Origin/CSRF,
ошибки, request_id, no-store и неизвестные поля применяются без ослабления.
GET не запускает работу. Доступ — текущий Member (включая Owner/Approver).

### POST p/runs

Обязателен `Idempotency-Key: <uuid>`. Закрытая форма тела:

```json
{
  "operation": "inspect_text",
  "inputs": [
    {"kind": "source", "id": "<uuid>", "state_id": "<uuid>"},
    {"kind": "document", "id": "<uuid>", "state_id": "<uuid>"}
  ]
}
```

inputs: 1–32; один материал не повторяется, даже с другим state_id. Все refs
сервер проверяет внутри проекта. Нужны текущие доступные состояния; чужой/
несуществующий материал даёт одинаковую 404; прежний state своего материала —
409 input_changed; state_id другого собственного материала — 422 invalid_input.
Запуск всех начальных units создаётся одной транзакцией: частичного HTTP-успеха нет.

### GET p/runs/{run_id}

Ответ 200 или одинаковая 404 для недоступного/чужого run. Форма Run:

```json
{
  "id": "<uuid>", "operation": "inspect_text", "execution_kind": "technical",
  "ai_performed": false, "state": "queued", "created_at": "<UTC RFC3339>",
  "units": [
    {
      "id": "<uuid>", "input": {"kind": "source", "id": "<uuid>", "state_id": "<uuid>"},
      "state": "queued", "retry_of_attempt_id": null, "attempt": null
    }
  ]
}
```

Для существующей попытки attempt содержит только id, request_id, state,
started_at, finished_at (null до завершения), reason_code (или null),
result (null либо `{id,character_count,utf8_byte_count,created_at}`). Lease,
owner_token, SQL/исключения и тексты не возвращаются. Units сортируются по id.
Агрегат run: все queued → queued; есть queued/running → running (в том числе
часть уже конечна); все completed → completed; все cancelled → cancelled;
все failed → failed; остальные полностью конечные комбинации → partial.
Для точного различения queued/running клиент читает также units; partial не
выдаётся за полный успех. Один GET использует согласованный read snapshot,
чтобы состояние и units не относились к разным коммитам.

### POST p/units/{unit_id}/retries

`Idempotency-Key: <uuid>`; тело `{ "expected_attempt_id": "<uuid>" }`.
Только failed, текущие права и прежние входы не изменены. Создаёт новый run
с одной queued-unit, тем же входом и retry_of_attempt_id. Старый run/attempt
не переписываются. Retry-попытка появляется при захвате worker, не при HTTP POST.
completed/running/queued/cancelled или неверный expected_attempt_id →
409 retry_not_allowed. Изменённый вход → 409 input_changed: нужен новый start.
Два разных ключа не создают две ветви: UNIQUE retry_of_attempt_id, проигравший
получает 409 retry_already_requested. Повтор той же команды с тем же ключом
возвращает тот же новый run, без новой unit.

Оба POST отвечают 202 той же формой Run; при повторе ключа — актуальное
представление прежнего run. Сначала повторно проверяются доступ и fingerprint,
потом возвращается прежний run. Тот же ключ с другим телом → 409
idempotency_conflict; отсутствие/неверный UUID ключа или неверное тело → 422.
GET требует сессию; POST — дополнительно Origin и текущий CSRF. POST не
повторяется клиентом автоматически. 202 означает сохранение команды, не её успех.

## 4. Транзакционный протокол

Один worker последовательно исполняет задания. Короткие write-транзакции
READ COMMITTED используют порядок `Project FOR UPDATE → unit → attempt`.
Он совместим с текущим управлением правами И1/И2а. Unit выбирается как кандидат
без удержания блокировки, затем под блокировкой проекта состояние проверяется
заново. Проектные блокировки не удерживаются во время вычисления/ожидания.
Масштабирование на несколько worker этим проектом не утверждается.

1. **Start/retry:** блокировать Project; проверить права; обработать
   идемпотентность; проверить refs/предусловия; вставить run/units; commit.
   Конкурентный повтор после ожидания читает уже сохранённую команду.
2. **Claim:** выбрать старейшую queued по (created_at,id); блокировать Project,
   unit; снова проверить queued, доступ инициатора, доступность и current_state.
   Вставить running attempt с новым token; unit → running; commit. При
   отозванном доступе/изменённом входе сразу создать cancelled attempt и
   cancelled unit с причиной; никаких результатов.
3. **Compute:** получить только нужный текст в короткой read-транзакции,
   закрыть её, вычислить числа в памяти. Текст не попадает в очередь/логи.
4. **Heartbeat:** отдельное соединение/короткая транзакция в том же порядке;
   условно продлить lease при matching token, running, неистёкших lease/deadline.
   Нельзя оживить уже истёкшее владение. Срок не превышает абсолютный deadline.
5. **Complete:** снова блокировать Project/unit/attempt; проверить token,
   сроки по clock_timestamp(), права инициатора, текущий вход и вид/доступность
   материала. Вставить один technical_result; оба состояния → completed;
   отозвать token/lease; проставить finished_at; commit одной транзакцией.
6. **Ошибка/отмена:** в том же протоколе записать только безопасный reason_code,
   оба конечных состояния, finished_at; отозвать владение. Содержимое exception
   и текст не сохраняются. Зависимых этапов/автоматического продолжения здесь нет.

Приоритет проверки в completion: существование проекта/владение/срок →
текущие права → текущий вход → результат. Истёкший владелец не меняет попытку,
включая её причину; recovery завершает её как failed. Изменённый вход или
утраченное членство отменяет результат. Чужой выход не публикуется даже при
совпадающих числах. Успех одной unit не откатывается при ошибке другой.

## 5. Восстановление и остановка

Технические начальные параметры: poll=1 s, heartbeat=5 s, lease=20 s,
deadline=60 s, stop grace=30 s; конфигурация требует heartbeat < lease < deadline.
Это параметры инженерного исполнения, а не SLA или продуктовые лимиты.

- Перед циклом worker выполняет только check_schema из DEC-011. Неверная/старая/
  более новая схема — отказ до claim, без DDL. Проверка повторяется после
  восстановления соединения и перед claim; обновление несовместимого образа
  предполагает остановку старого worker, а не online-обновление под ним.
- При старте и в каждом цикле выполняется recovery: найти кандидатов running
  с lease/deadline <= времени БД; для каждого под Project/unit/attempt lock
  заново проверить истечение; failed с deadline_exceeded (приоритет) либо
  lease_expired; token/lease NULL; finished_at. Recovery идемпотентен.
- Неистёкшая попытка другого процесса ожидает срока: restart сам по себе не
  доказывает потерю. queued сохраняются. Failed требуют ручного retry; нет
  автоматической передачи running обратно в queued и повторного исполнения.
- При разрыве БД heartbeat не подтверждён, новое задание не берётся. Повтор
  соединения с интервалами 1,2,4,8,15 s (далее 15). После восстановления —
  check_schema/recovery и проверка владения; просроченный результат отбрасывается.
- При неизвестном результате COMMIT worker перечитывает attempt/result по
  известным UUID. Уже completed — успех без повторной вставки; ещё running —
  завершение допустимо лишь с прежним действующим владением. UNIQUE attempt_id
  и условные переходы исключают вторую публикацию. Запуск вычисления после
  неизвестного claim также начинается с перечитывания, не с новой попытки.
- SIGTERM прекращает claim; текущая короткая операция может завершиться в grace.
  При принудительной остановке lease истечёт и recovery запишет ошибку. Чистое
  завершение закрывает соединения/heartbeat. Тестовая задержка не входит в
  production-операцию; сбои моделируются тестовым инструментарием.
- Healthcheck проверяет свежесть реального успешного цикла и доступность/схему
  БД, а не только наличие PID. Состояние готовности хранится локально в tmp,
  без текста/токенов. При недоступной БД/зависшем цикле healthcheck неуспешен.

Для AI-этапа отдельно проектируются много-входовые зависимости, области охвата,
содержательный приём, хранение находок, переходы зависимых units и их HTTP/UI.
Неизвестные поля/операции сейчас отклоняются; очередь не запускает весь срез.
При существенном усложнении по DEC-006 прежде сравнивается готовое минимальное
решение. Redis/Celery не добавляются.

## 7. Критерии приёмки И2б

| Проверка | Наблюдаемое нарушение, которое должна выявить |
|---|---|
| Миграция empty / populated m02a / повторный upgrade | Потеря старых пользователей, сессий, проектов или точного текста; нарушение FK/CHECK/UNIQUE. |
| HTTP start/get/retry, Owner/Member/Approver/outsider | Подмена проекта/автора, чужие refs, обход Origin/CSRF, утечка текстов или токенов. FR-003/032, AC-01. |
| Реальные Unicode/LF/CRLF тексты обоих видов | Неверные char/UTF-8 числа, нормализация исходника, фиктивный успех без чтения/записи. Технический базис FR-004, не приёмка AI. |
| Идемпотентность и гонки двух POST | Два run под одним ключом, иной payload под тем же ключом, две ветви retry. |
| Отзыв членства между claim и completion | Сохранение результата после потери прав; согласованность с Project lock И1/И2а. |
| Изменённый/чужой state и гонка смены current_state | Публикация по устаревшему входу. Смена моделируется транзакцией теста, нового API правок не добавляется. |
| Worker restart: queued, running до/после lease, failed | Потеря задания, раннее объявление потери или автоматический retry. |
| Lease/deadline heartbeat и поздний старый владелец | Продление истёкшего владения, превышение deadline, повторная публикация. |
| Разрыв БД до/после claim/complete COMMIT | Дубли attempt/result, принятие недоказанного COMMIT за отказ и повтор операции. |
| Две независимые units, одна failed | Откат успешной unit либо ложный общий completed. |
| SIGTERM / принудительное завершение / restart БД | Новые claims после остановки; вечный healthy при потере связи/зависшем цикле. |
| Старая/более новая схема и отсутствие прав DDL у worker | Начало обработки до совместимости или скрытый запуск миграций worker. |
| Runtime/HTTP/log inspect | Текст, пароль, owner_token или AI-фикция в техническом результате/логах. |

Проверки транзакций и восстановления выполняются на настоящей изолированной
PostgreSQL; SQLite не используется. Внешние AI-вызовы отсутствуют. Достижение
AC-02/03/05 и содержательная работоспособность AI этим этапом не заявляются.
До реализации после согласования составляется адресное FR/AC → тест соответствие.

## 8. Объём запрашиваемого утверждения

Утверждение этой ревизии разрешит только четыре таблицы m02b, inspect_text,
три описанных HTTP-контракта, транзакции/recovery и работающий worker без AI,
необходимую синхронизацию документации/Compose/CI и перечисленные проверки.
Оно не утвердит весь FIRST_TEXT_SLICE, дальнейшие AI-операции, UI обработки,
редактирование/удаление материалов или платные интеграции.
Реализация и миграция И2б пока отсутствуют; независимое ревью спецификации
не выполнено. Перед реализацией нужно отдельное явное согласие пользователя.
